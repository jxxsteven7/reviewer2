# Architecture

How the app is put together. The constraints are in [rules/constraints.md](rules/constraints.md), the first game's rules in [games/keywords.md](games/keywords.md), the second game's in [games/impostor.md](games/impostor.md).

## One process, one port

One Node process serves everything on one port: the built front end, `/healthz`, the lists of thanks and the account API under `/api/`, avatars under `/avatars/` and Socket.IO under `/socket.io/`. Rooms live in memory and end with the process; feedback and accounts are in a SQLite database, avatars as files beside it ([Data](#data)). The only other things, serving no player, are the operator's status data, as JSON on a second port reachable only locally ([Status](#status)), and the mailer, a program of its own that alone holds the mail service's key and talks to the internet; the game server asks it over a Unix socket to send a mail, and needs no internet itself ([Mail](#mail)). The agent is another such program, which asks a language model for the moves of the AI players ([The agent](#the-agent)).

| Layer | Where | What it does |
|---|---|---|
| Shared | `shared/src/` | Types and rules both sides run; `schemas.ts` and `schemaParts.ts` for the server and the agent alone |
| Shared games | `shared/src/games/<game>/` | Each game's own types and rules, imported by its own path, `@reviewer2/shared/<game>`, and its schemas, `@reviewer2/shared/<game>/schemas`, for the server and the agent alone |
| Server core | `server/src/core/` | Rooms, players, connections, limits, the word library |
| Server games | `server/src/games/<game>/` | One module per game: seats, rules, views |
| Server accounts | `server/src/accounts/` | Logins, the account API, email, avatars |
| Server store | `server/src/store/` | The database and what is kept in it |
| Mailer | `mailer/` | Sends the mails of accounts ([The mailer](#the-mailer)) |
| Agent | `agent/` | Asks a language model for the AI players' moves ([The agent](#the-agent)) |
| Client core | `client/src/core/` | Connection, rooms, lobby, language |
| Client games | `client/src/games/<game>/` | Each game's screens |

## Rooms

- **Codes:** four characters of Crockford's base32, shown as `R2-K7QX`, linked as `/room/K7QX`; `parseCode()` in `shared/src/codes.ts` reads them. Codes are reused, so every snapshot carries a random `roomId`.
- **Phases:** `lobby`, `playing`, `ended`, back to `lobby`. Each game has a random `gameId`. A room can be a [match](#matches).
- **The chair** is the first member and alone changes settings, starts and ends games and matches, shuffles, benches, removes, invites AI players ([AI players](#ai-players)), hands the chair on, or closes the room. When the chair leaves, or is offline for 3 minutes, the earliest-joined online member takes over, never an AI player.
- **Playing or watching.** A newcomer sends `play: true` to play; the game decides what that means ([seats](games/keywords.md#seats)). A returning member keeps their seat. A removed one stays out by their member key, which is the account's for a player who is logged in and the browser's otherwise, and by the keys of the browsers they were connected from: for as long as the room lasts (`removed`) if it was public when they were removed, and for 2 minutes (`removed_recently`) if it was private, whatever it becomes later. A room remembers its last 200 removals.
- **Revisions.** Every change bumps `rev`.
- **Screens,** such as a projector, watch without a token or seat, through `room:watch`, with a spectator's view; up to 5 per room. In a public room a screen takes an account with a seat there, one screen each ([Public rooms](#public-rooms)).

## Public rooms

- **Listing.** A room is private unless its creator makes it public, or the chair does in the waiting room (`room:public`). The home page lists public rooms (`meta:rooms`): code, game, language, fields, or that every game draws them anew, for a game that uses the word library ([Games](#games)), member count and whether a game is on; no full rooms or rooms with nobody online; at most 50, waiting rooms first, then the oldest. A game may keep a room set up for people who know each other private (`GameModule.mayBePublic`, and the game's own settings, `private_only`): in the second game, a room with a setter ([games/impostor.md](games/impostor.md#the-setter)) or one that shows those who only watch every role and both words, which can't be made public, nor a public room set up so.
- **Accounts.** Creating, listing or joining a public room, by the list, code or link, takes an account (`account_required`), so that players can be reported and barred. Guests and screens already in a room stay when it is listed. A new screen there takes an account with a seat (`not_member`), one each, a new one replacing the old.
- **Reports.** A member with an account may report another (`room:report`). The `reports` table (migration 6) keeps who reported whom, the name they had, the room's code and the note, for `admin.cjs reports list`; it is an archive ([Feedback](#feedback)).
- **Bars.** `admin.cjs accounts bar` keeps an account out of public rooms (`public_barred`), not private ones. A public room whose chair could no longer list it, a barred account or a guest, goes off the list by the next sweep; everyone in it stays.

## Players and identity

- **Tokens.** A browser gets a random 32-byte token on its first connection and keeps it in local storage. Every connection first gets `session`, with the server's `version`, the `account` logged in (or null) and, when just issued, the `token`.
- **Member keys.** The server never stores tokens; it works with the token's SHA-256, which never leaves the server. An account's key is the SHA-256 of its ID, so an account is one player on every device.
- **Names.** A member with an account goes by its username. A guest gives no name: the room numbers its guests in the order they first come in, from 1 (`PlayerView.guest`), never giving a number twice, and a guest who leaves and comes back with the same member key has their number again, for as long as the room remembers the key (the last 500, `MAX_GUESTS`). The client calls a guest "Guest 3", in the interface's language, with the first character of that word as the avatar (`client/src/core/names.ts`); the server's own name for them, in what it says itself, such as a report, is the English one. A guest who logs in leaves the number behind. No username may be a guest's name, in either language, or one of the reserved names (`isReservedName` in `shared/src/accounts.ts`). The rules for names that people write, such as a username, are in `shared/src/names.ts` and `shared/src/text.ts`, shared with the client.

## Messages

Everything after the page load goes over Socket.IO, except the account API ([Accounts](#accounts)). `shared/src/protocol.ts` describes the room messages; each game adds `<game>:<action>` ones.

- **Answers:** `{ ok: true, ... }` or `{ ok: false, error }`; an unknown message is `bad_request`. The client shows `errors.<code>` from the locale files.
- **Validation:** every payload against a zod schema from `shared/src/schemas.ts`, or, for a game's own messages, from its folder's `schemas.ts`, both built of `shared/src/schemaParts.ts`, which the client never imports (ESLint refuses them): zod probes `new Function`, which the Content Security Policy forbids.
- **In order:** one connection's messages run in arrival order, and handlers never await between reading a room and writing it.
- **Snapshots.** After every visible change, each connection gets its own complete `room:state`; the client keeps the highest `rev` for its `roomId`.
- **Closing.** `room:closed` says why a room is gone: `removed` or `removed_recently`, as `room:join` would then answer, `dismissed` (a screen the chair sent away), `expired`, `left`, `closed` or `restart`.

## The handshake and reconnecting

The handshake carries `{ token, code, roomId }` (a screen `{ watch: code, roomId }`), and a member's connection is put back into its room before any message runs. It only brings back: its one answer is `room:closed` with `expired` for a `roomId` the code no longer has, so the client always follows it with `room:join` or `room:watch`. A screen's page keeps the code and ID of the room it showed last in the browser's storage, so that reloaded it comes back by the ID, as a busy server asks ([Limits and housekeeping](#limits-and-housekeeping)); told `expired` of an ID it had only remembered, it drops the ID and goes on by the code alone.

The home page asks `meta:seats` once connected, after every reconnect and when it hears `room:closed` (a connection that came from a room's page is still in it), and offers a way back to each room where the connection still has a member's seat, never taking the player there by itself. Seats are found by the connection's key, its account's on every device, or by the guest seat its account would adopt; the answer gives each room's code, game and whether a game is on (`playing` until the room is back in the waiting room), at most 5, the newest first. It looks up no code, so it doesn't count against an address's codes.

## Games

A game implements `GameModule` (`server/src/core/game.ts`), and the server plays those in `GAMES` (`server/src/games/index.ts`): the first game, `keywords`, and the second, `impostor`, in beta ([games/impostor.md](games/impostor.md#beta)). The core owns the room, its members and the chair; the module owns its data and decides seats, settings, starting, messages, deadlines, views and matches. Its data is immutable. `views()` is the only way its data leaves the server to players, called once per snapshot for each member and the screens. A module also says what the record of a game keeps of it ([Game records](#game-records)), and what each player's part in a game that finished was (`PlayerResult`): won, drawn or lost, and the place, 1 and one more for each player who did better, so that players level share it, which lets a game have two groups, more, or none; with the detail of its own scoring in a shape of its own (`detail`), which the core keeps and never reads.

**Scoring.** A game scores itself (`GameModule.score`): each player's points as they stand, the end included once it has ended, which the [ranks](#academic-ranks) take and a [match](#matches) adds up, and a game without it brings nobody points. A game may also count for nothing for a reason of its own (`GameModule.scoresNothing`), as one of the second game in which the chair removed a player ([games/impostor.md](games/impostor.md#leaving)), which the chair could otherwise win by removing others: the room tells the game when a member goes because the chair removed them (`GameModule.leave` with `removed`), and such a game brings nobody points or a title, while its record keeps it in full. A game says how large the log of one of its games may grow, where it needs more than most (`GameModule.logLimits`, [Game records](#game-records)).

**Words.** A game says what it takes from the word library (`GameModule.words`): a board of words (`board`, 25 for the first game), of which no two clash (`clash`, [games/keywords.md](games/keywords.md#setting-up)), or a pair of related terms (`pair`, the second game, [games/impostor.md](games/impostor.md#the-words)), each word with its term's ID and field (`BoardWord.term`). A game without it uses no word library: its rooms have no fields and draw none at random, and neither the room's view nor the public list carries fields for it (`RoomView.fields`, `PublicRoom.fields`). Only a game with a board takes words of the chair's own ([custom words](games/keywords.md#custom-words)). A game may bring its own words for the game about to start (`GameModule.drawsWords`), as the second game does when a setter gives them: the room then draws none, and a game of pairs may have no fields chosen at all, though one that is to draw from none can't start (`no_words`). The library also reads the English meanings of the Chinese characters of its lists, from `words/dictionary/han-glosses.json`, which the cards carry for the clue check ([games/keywords.md](games/keywords.md#the-clue)); without the file it has none, which the line `word_lists_loaded` says (`glossed`). It reads the pairs of each list from the terms' `related` ([../words/README.md](../words/README.md#related-terms)), each a pair only with words in every language, and every field says how many pairs it has (`FieldInfo.pairs`). The room draws from the chair's fields, unused words first. A room may instead draw its fields anew for every game (`randomFields`): at each start every field with enough words in the room's language for a game of its own, a board's worth or a pair, goes in on the toss of a coin, and one of them at random when none does (`drawFields()` in `shared/src/protocol.ts`, which the room setup's "choose at random" uses too). It then needs no field chosen, and keeps those chosen for when the chair turns it off. Nobody is told which fields a game drew but its record (`fields`); the public list says that the room draws them. `drawWords()` in `server/src/core/words.ts` takes the words of a board in random order and keeps each that clashes with none kept before; `scripts/check-words.mjs` makes sure each list has enough such words ([../words/README.md](../words/README.md#contributing)). If short, it draws again, each time the word with the fewest clashes; when some clash all the same, the game starts and the server logs `words_clashed`.

**Pairs.** `drawPair()` in the same file draws a pair from those of the fields, leaving out every pair that 2 or more players rated as having a problem (`PAIR_PROBLEMS`, [Ratings](#ratings)). It prefers, in turn, a pair that the room hasn't played, which it remembers by the pair's key for as long as it lasts (`pairKey()`: the field and the IDs of the two terms, which never change), and that no two of the members with accounts in the room have had in one game together; then one the room hasn't played; then any. Of those, it takes one that those members have had the fewest times, all of them together, and the more players rated a pair good, the likelier it is. What it knows of the members' games and of the ratings is counted from the records for each draw (`RatingStore.pairRecords` in `server/src/store/ratings.ts`, by the pair's key in the record's setup, `GameModule.setupPaths.pair`), and nothing of it is kept; without the records, or when they can't be read, the room goes by its own memory alone.

**Time.** A module says when it next has something to do with `deadline()`. The server keeps one timer per room and calls `tick()` when it fires and before every game message, so an action for a turn whose time ran out is `stale` even before the timer fired.

**Errors.** A module that throws leaves the room as it was; the message is answered `internal` and logged.

**On the client.** Each game's screens are in `client/src/games/index.ts` (`GameScreens`): its waiting room, the game, the big screen, the replay, its settings and its rules, with, for a game that has them, the choice of where its words come from (`Source`), its matches' own options and, for a game that takes only some numbers of games, those numbers, offered as pills (`match`), and its tutorial (`guide`). What the pages around the games know of each, without its screens, is in `client/src/games/info.ts` (`GameInfo`): the games in the order the home page shows them, each on a card of its own, whether a game is in beta, which its card, room setup, practice sheet and tab of the record say ([games/impostor.md](games/impostor.md#beta)), its roles and titles, whether its matches award titles (`matchTitles`), which word lists serve it, whether it draws its words from them and whether a room may be listed with the settings chosen, and its record as counts ([Accounts](#accounts)). The room setup shows the lists only while the game draws from them, the kind of room only for a game with matches, and a public room only where the game allows it.

## AI players

The chair invites Reviewer 1 (`AGENT_PERSONAS` in `shared/src/agent.ts`) to a seat with `room:addAgent`, as the game reads it (`GameModule.seatAgent`), where it plays like anyone, through the rules: in the first game to a group's, as its PI or one of its students, a group having one AI PI and one AI student at most (`agent_limit`); in the second to a place at the table for the next game, as many as there are places (`table_full`), where it describes its word, votes, judges reports and guesses the students' word once it was voted out, where the room allows it, but never reports anyone, never talks off the field and never sets the words ([games/impostor.md](games/impostor.md#ai-players)). While they are tried out:

- **Who may.** Only a chair whose account the operator lets have them (`admin.cjs agents allow`, the `agents` column of `accounts`, migration 15), or the chair of a [practice room](#practice-rooms), in a private room that plays no match, on a server with an agent (`AGENT_SOCKET`); `RoomView.agents` says whether the chair may now, and the client shows nothing of them otherwise. Elsewhere `agents_not_allowed`. A room with AI players can't be listed or play a match (`agents_in_room`). Those in a room stay when its chair could no longer invite them.
- **Members.** An AI player is a member with a persona (`PlayerView.agent`), which the client names it by, and no connection, browser or account. It counts toward the room's 30, never chairs (`player_is_agent`), doesn't watch, and keeps no room alive: the AI players go with the last person, and a room where only they are online closes as one with nobody online does. The chair removes one with `room:remove`, or with `room:spectate`, which removes it just the same, and may invite it again; the shuffle leaves its seat alone. It is online while the agent answers, so a game of the first game can't start with an AI PI offline (`captain_offline`), and one of the second plays without the AI players that are offline. While the agent doesn't answer, no AI player can be invited (`agents_offline`): the waiting room of a room that may have them says so (`RoomView.agentsOnline`), which the driver asks again as the room changes, as for the home page ([Practice rooms](#practice-rooms)), and holds the chair's invitations back.
- **Before a game.** An AI player can be invited once a person has a seat, in a group or at the table (`needs_human`, as a refusal and as a start problem), so that a room is never the AI players' alone, and with AI players seated every time limit must be on (`needs_timers`; in the second game those of the descriptions and the votes), so that a slow or missing agent never holds a game up.
- **Playing** (`server/src/core/agents.ts`). After every change, the driver asks the game what each AI seat is to do (`GameModule.agentTask`), asks the agent with that seat's own view, and sends the messages that the answer makes (`GameModule.agentMove`) through `Room.act()`, at a pace that people can follow. An answer for a moment that has passed is dropped, and no AI plays on in a game that every person has been offline in for 20 seconds; until then, the one person in a room may reload without an AI dropping what it was doing. A request that brings no answer (`busy`, `no_answer`, `no_legal_clue`, `no_legal_move`) is made again after 10 seconds, then after twice as long each time up to a minute, for as long as the phase lasts. When the agent can't be reached, or its model's service is gone (`model_failed`), the agent is down (`agent_down`) and its players are offline until a ping every 30 seconds finds it back (`agent_up`); the clocks carry the games on meanwhile.
- **Playing for someone offline.** In a room of the first game where the chair may invite AI players, a person who has been offline for 20 seconds while it is their turn is played for by an AI, unless a person of their group can play the turn (`GameModule.agentTask`, which the second game gives for its AI players' own seats alone: there, a person whose time runs out misses their turn); until then they count as there, so that a reload or a locked phone changes nothing of what any AI does. One AI plays the guesses of a group: its AI student, if it has one, or else one of its offline students. Whoever is played for is marked (`PlayerView.takenOver`) from the moment an AI is set to play for them, as it is asked what to do, until they are back, when it stops at once.
- **Points.** A game in which an AI played, as a player or for someone offline, is on the record as any game, which the record of the game says (`agents` and `takeover` in `replays`, migration 15), but brings nobody points, a streak, a [title](#titles) or a [friend title](#friend-duos), unless every answer the AI gave in it came from a certified version of the AI: the version of the prompts and the model, which the AI log notes with each answer ([Game records](#game-records)), among those the code certifies (`CERTIFIED_AGENTS` in `server/src/core/agentLog.ts`, `certifiedPlay()`), which the room and the recount decide by. None is certified yet, so every such game brings nothing; the first to be certified also changes the records page, the score floats and the check of the data, which still take "an AI played" for "brought nothing", as a test says (`agentLog.test.ts`), and when a game is kept as one that brought nothing, which the streaks and the friend duos go by (`scores_nothing` in `replays`).
- **The record** names the AI players (`agents` in the log), marks every move made for someone offline with the persona (`agent`), and keeps the AI's own log beside the game's ([Game records](#game-records)).
- **Its page.** Anyone may open an AI player's page in a room, from its avatar (`AgentProfileCard.vue`, in its panel; `GET /api/agent/<persona>`, `AgentProfileView`): player number 0, which no account has, a line about it, how many of it are in the rooms now, as AI players and playing for someone offline, and in how many rooms, counted as the page is read (`agentsIn` in `server/src/core/agents.ts`); and what it has done in the games that finished, as counts alone, for each game apart (`AgentProfileView.games`, by game ID), which the page shows game by game, under the game's name, leaving out a game it has played none of, on blocks as a player's record (`StatBlocks.vue`): the games, and the share of its seats in them that it won, in all and in each of the game's roles, each over how many seats, since it may sit in both groups of one game of the first game, as it does in a practice room, where a game counted as won whenever one of its seats won would be won every time; then, for the first game, the cards its clues found per clue, the clue that found the most, how often it revealed Reviewer 2, and the games it played in for someone offline. An account also sees, apart, in each game, what it has played with it: the games on its side and against it, won and lost, and those it was played for in. The counts come from `agent_plays` (migration 15), a row for each AI player in a seat at the end of a game that finished, naming the game, with its result and place as the record counts a player's (migration 26) and what the game counts of it as JSON in the game's own shape (`feats`, `GameModule.agentFeats`, migration 23), which the game adds up for the page (`GameModule.agentTotals`), or none for a game that counts nothing of it, as the second game, and one for each person it played for, with no result or place, with their account, which is forgotten when the account is deleted, and no counts. It is in no ranking and has no friends.

## Practice rooms

Anyone with an account may play a game with Reviewer 1 from the home page: "Play with Reviewer 1" in each game's card opens a sheet that asks who plays, the player alone or with friends, and for the language and the word lists, folded into a line that names them; for the player alone, in a game with more than one role to pick (`GameInfo.practiceRoles`), the role too, and shows who then sits where, the two groups in the first game and a row of avatars in the second, where everyone plays alone; a game in beta says so. The role and the lists are those of the account's last practice room of the game ([the last room setup](#accounts)), or of the browser's from before, kept in local storage, which keeps the first game's role alone, or the first game's PI and the general list. `room:create` with `practice` makes a private room (`Room.practice`) with the game's default settings, which plays no match. For the player alone (`who: 'me'`, with the role as the game names it), the creator sits where the game puts them for that role, Reviewer 1 takes the other seats (`GameModule.practice`: for the first game the red group's other role and the blue group's two; for the second, whose one role is `player`, five places at the table, for a game of six), and the game starts once the creator is in the room. With friends (`who: 'friends'`), the room opens in its waiting room, as a room from "New room" does: the creator sends friends the link, sits, and invites Reviewer 1 to the seats nobody takes, whatever their account ([AI players](#ai-players)); the sheet keeps the lists for the next time and leaves the role as it was. A guest is refused (`account_required`), whom the home page asks to log in or register; so are a role that the game doesn't have, a game without practice rooms, and `practice` with `match`, `public`, `settings` or `randomFields` (`bad_request`). While the agent doesn't answer, there are none (`agents_offline`): the home page asks with `meta:agents`, when it opens and when the sheet does, and greys the button out; on a server without an agent, which answers `available: null`, it shows no button at all. Nothing asks the agent while no AI plays, so `meta:agents` answers what the agent said last and, if that was more than 30 seconds ago (`FRESH_MS`), asks it again for the next answer (`AgentDriver.recheck`): a model that went away meanwhile is found out before the player has picked a role. A refusal leaves no room behind.

In its waiting room, from the start for a room with friends and after the first game for one made for the player alone, a practice room is a private room like any other, which the chair may invite AI players to, whatever the chair's account, and where an AI plays for someone offline. It stays one whoever chairs it. Each of its games says so in its record (`practice`, migration 18), as a fact of the game: whether AI players were in it is in `agents`. There is no limit of its own on how many there may be at once; the agent's queue (`AGENT_QUEUE`) is the limit there is.

## The tutorial

The tutorial at `/guide` teaches each game and the site in chapters of steps, in the browser alone: it sends no game message, and changes nothing on the server, which it only asks what the home page asks, whether the AI players answer and which word lists there are. Its contents list each game's chapters, which the game names (`GameScreens.guide` in `client/src/games/index.ts`), for a game that has them, as the second game, in its beta, doesn't yet, and then the site's (`client/src/core/guide/chapters.ts`): for the first game, the rules in brief, playing a student, playing the PI, more in a game and room settings, and for the site, the account and its public page, rooms and invitations, the waiting room, friends, ranks, titles and streaks, and feedback. Each step has an address of its own, `/guide/<chapter>/<step>`, which the browser's back and forward go through, and a coach card with its text, under `guide.chapters` in the locale files, which leads back and on, as the arrow keys do. How far this browser has read each chapter, and the chapter read last, which the contents offer to go on with, stay in local storage (`r2.guide`, `client/src/core/guide/progress.ts`), which is all the tutorial keeps there; the tutorial works without it.

- **Scenes.** A step shows a scene made of the game's or the site's own components, with invented players, words and clues (`client/src/games/keywords/guide/demo.ts`), never a real player's data: the components that load an account's friends, records or likers are left out, the room setup starts from its defaults rather than from the reader's last room, and the site's scenes take no input. In a game's chapters, only the part that the finger is at takes a tap, which goes on to the next step, or, for a card that the finger holds down, opens the game's menu of marks; a PI's clue is typed and checked as in a game (`PlayScene.vue`); the strip above the board changes no tab title, its clock stands at what the step gives, and the group chat keeps nothing as read (`demo`, in `TurnStrip.vue` and `GroupChat.vue`). The finger (`GuideFinger.vue`) taps, holds or points at the part (`spot.ts`), which the page brings into view between the chapter's bar and, on a phone, the coach card.
- **Ways in and out.** The first game's card on the home page offers the game's tutorial, as a green sticker to a guest and to an account that hasn't played the game, and as a small word beside the rules to one that has (`played`, [Accounts](#accounts)); the rules end with a way to it, which a room opens in a new tab. A chapter's last step leads on: to a real game with Reviewer 1 in the role that the chapter taught (`/?practice=<role>`, which opens the [practice sheet](#practice-rooms) with that role chosen once the AI players answer, and brings its button into sight while they are offline), to the next chapter, or to the place on the site that it is about, such as the room setup (`/?create=1`), the practice sheet for a room with friends (`/?practice=friends`), or the feedback panel itself. On a server without an agent, the ways to the practice sheet lead to the next chapter instead.

## Replays

The players with accounts can watch a game that finished again, and nothing of it is kept apart: `POST /api/account/replay` with `gameId` works the replay out from the [record of the game](#game-records), how it began and its log, as the game says (`GameModule.showReplay`), and sends it, keeping nothing. A replay belongs to the game, not to an account: it goes to an account that took part in the game, as `game_players` says, one that played in it, those who left during it included, or one that gave its words without playing, as the setter of a game of the second game (migration 27), and `no_replay` to anyone else, as for a game that didn't finish. The account page offers it from the lines of its record ([Accounts](#accounts)). Deleting an account deletes its rows in `game_players`, and the replay stays for the others who took part in it.

**A replay keeps no name.** For the first game, the server plays the game through again from how it began, the board with every color, the group that started and the settings, with every move in its log, by the functions of the rules that made them (the `apply` functions of `server/src/games/keywords/rules.ts`), which check nothing: the log holds only the moves that the rules took, under the rules of their time; what a move was, such as one in the last seconds of its phase, is as the rules say now. That gives the clues and the guesses, who gave each clue and revealed each card, by player ID, when each came, the cards each PI meant, every turn whose time ran out, with the PI it cost, and the result; and the two groups as the game ended, each PI and its students by player ID, from where everyone sat as it began and every seat taken, changed or left during it, in order. The answer is the replay as it is shown (`ShownReplay`), with who everyone in the groups and the record was: an account by its username, avatar and handle as they are now, from `game_players`, an account deleted since as a deleted player, by the log's `deleted`, a guest by their number in the room and an AI player by its persona, as the log names them, and the player ID that the account asking had, which its group's bar shows first. The page shows a replay with the groups' bars and lets anyone open a panel from an avatar there, with the moves of that player ([games/keywords.md](games/keywords.md#replays)).

For the second game, the server reads the replay from how the game began, with every player's number and role and the two words, and from the entries that its log keeps of what the moves came to (`shownReplay()` in `server/src/games/impostor/replay.ts`): every line, and every one whose time ran out, every vote revealed, every report settled with everyone's verdict, every guess of the students' word, who went out how and in which round, the result and everyone's points, all by number; with who everyone was, the setter among them, as for the first game (`peopleOf()` in `server/src/core/game.ts`), and the player ID that the account asking had. Only a finished game has one, a game that Reviewer 2 left included; and a person who still has to guess the AI players of the game, in the room that has just played it, gets it once they have ([Guessing the AI](#guessing-the-ai)).

## Game records

The record of a game (migrations 12 and 15) is one row in the `replays` table, on the server alone: no API, page or command sends it anywhere but the replay worked out from it, which goes to the accounts that played in a finished game ([Replays](#replays)). Every game is kept, however it ended and whoever played in it, guests alone included, and a game with the chair's own words like any other, each such card marked ([custom words](games/keywords.md#custom-words)). Every other row of a game's data, the records of its players, who was who, what the AI did, and what its players said of it, their [ratings](#ratings) and their [guesses of the AI players](#guessing-the-ai) (migration 27), points at it by the game's ID and the game (`FOREIGN KEY ... ON DELETE CASCADE`, migration 24), so that nothing of a game outlives its record or belongs to another game; feedback sent about the game and the words adopted from it ([Content contributions](#content-contributions)) name it too, and outlive it, forgetting it (`ON DELETE SET NULL`). What the record of the game says is kept there alone: who won, when, whether an AI played, and the game's place in its match. The records are for training and testing the AI players and for research, so each says what kind of game it was, as facts of the game alone; whether a game is of use for some study, such as one that someone abandoned at once, is for whoever reads the records to decide, by rules of their own, which they can change and run again.

- **How it ended** (`ending`), set by the room: `finished`, by itself, such as when a group won; `withdrawn` by the chair, alone or with the match that the chair ended; `abandoned`, cut short when its room closed, whose log says why (`end` with `why`: `chair` when the chair closed the room, `empty` when its last person left, `idle` or `stale` when nobody was online, or nothing happened, in it for too long, `flood` when its log grew as large as a log may); or `interrupted`, cut short when the server stopped. Only a finished game has results, points, streaks, titles and a replay, and only it says who won (`winner`, none for a game that ends without a winner) and how (`reason`), in the game's own words (`GameModule.outcome`: for the first game, the group, and `found` when it found every card of its own or `reviewer2` when the other group revealed Reviewer 2; for the second, the side that won, a role, and how, [games/impostor.md](games/impostor.md#winning)). A finished game of the second game that a Reviewer 2 left has a replay and says how it came out, with no winner and `reviewer2_left`, but no results, points, streaks or titles ([games/impostor.md](games/impostor.md#leaving)).
- **What kind of game it was:** when it began (`started_at`) and ended (`ended_at`); how it began (`setup`, as JSON, `GameModule.setup`: for the first game, the settings, the group that started and the board with every color, each card marked as a word of the chair's own or of the lists, `custom`, and, on a board with some, who gave them, by player ID, `customAuthor`, which the games kept before migration 27 give as nobody, null; for the second, the settings, every player by player ID with their number, their role and whether an AI played the seat, the students' word and the Reviewer 2s' word, and where they came from: the word library, with the field, the pair's key and the IDs of its two terms, or the setter, by player ID, with the field they named and whether they asked to be named, [games/impostor.md](games/impostor.md#the-words)); how many played in it, by member key, those who left included, with an account (`accounts`), as guests (`guests`) and as AI players (`agents`); whether an AI played for someone who was offline (`takeover`); whether it brought nobody points, for whatever reason, as an AI that played in it or a reason of the game's own (`scores_nothing`, `GameModule.scoresNothing`, migration 27), which the streaks and the friend duos go by; whether it was played in a room that plays a match (`in_match`), and, for a game that the match scored, the match's ID, which game of it this was, from 1, and how many games the match was to have (`match_id`, `match_game`, `match_games`, migration 24); whether it was played in a [practice room](#practice-rooms) (`practice`, migration 18); its language and fields (`fields`, as JSON); and the versions of the server (`version`, `APP_VERSION`), of the game's rules (`rules`, `GameModule.rulesVersion`, which goes up with every change to the rules or the scoring) and of the word lists (`words`, the first 16 hex digits of the SHA-256 of the lists as read). A game kept has every one of these, but `setup` and `rules` where the game says nothing of them, and only a finished game has a `winner` and a `reason` (migration 22).
- **The log** (`server/src/core/gameLog.ts`, `log`): everything that changed the game, in order, from its start to its end. Each entry says when, in milliseconds from the start on the room's clock; who, by the player ID they had in the room, or nobody for the room itself; and what: one of the game's messages, as the game says to keep it (`GameModule.logged`), what the game keeps of a change of its own (`GameModule.logChanges`), such as how a group's marks stood when it revealed a card, when a turn ended and when the game ended, or one of the room's own events: joining and leaving, the chair benching or removing a player, the chair passing to someone else, an AI starting and stopping play for someone who is offline (`takeover`), a timer that changed the game, with those it was waiting for (`GameModule.due`) who were offline then, and the end, which for a game that didn't finish says how. It begins with where everyone in the room was, as the game describes each of them (`GameModule.seated`), which also says where the game put whoever came during it, and names the AI players among them by persona (`agents`), every guest who played by their number in the room (`guests`, by player ID) and, in a match, everyone in the room by their number in the match, with the numbers that have gone into another (`match`, [Matches](#matches)). **What a player said** in their group's chat is in it, apart, as the entry's `said`, so that whoever reads the records can leave it out, and so is what they said after the end, as the groups talk the game over: the log goes on after its `end` with the lines of the chat alone, until the room leaves the game behind, when the chair plays again or starts the next match, or the room closes, and those lines are then added to the kept log (`Room.review()`), with the accounts of player IDs that came after the end and, in a match, their numbers in it ([Matches](#matches)), but those of an account deleted meanwhile. Not in it: who went offline or came back, quick reactions, refused messages, those that changed nothing, and what the game leaves out, such as cards chosen and chosen again, and each mark that a group sets and changes. Nothing that happened in a game is ever dropped from its log, since the records are counted again from it (below). Every room holds its log in memory while its game is on, so past 48 KB of chat it keeps no more of it, and notes once that it left it out (`truncated`); everything else, which says who sat where and what they did, each member may add 200 entries to (`MAX_LOGGED_PER_MEMBER` in `room.ts`), a few times what a whole game takes a player, counted by member key, so that leaving and coming back starts no new count: past that the room refuses what they send and takes them in no more. Past 64 KB of it (`CROWDED_GAME_LOG_BYTES` in `gameLog.ts`), which guests coming and going under one browser key after another could reach, the log is crowded: the room takes nobody in and lets nobody change seats until the game ends (`room_crowded`), while the game's own moves, which are few, go on. The whole of it has 128 KB, which only a game left to its timers for hours reaches: the room then closes with the game cut short there (`abandoned`, `flood`), and the record keeps the whole log. A whole game makes a few kilobytes. A game that needs more says so (`GameModule.logLimits`): the second game, in which every player writes a line and votes every round, has 128 KB for the chat, 600 entries for each member, is crowded past 256 KB and has 512 KB in all (`LOG_LIMITS` in `server/src/games/impostor/index.ts`).
- **The AI log** (`server/src/core/agentLog.ts`; `agent_log` in `replays`, migration 15): for each step of an AI ([AI players](#ai-players)), when it was asked, the seat, the persona and whether it played for someone offline, the task, either the answer, in the game's own shape, with the agent's note (the model, the version of the prompts, how long it took, how much the model was let think (`reasoning`), whether the answer came from a question without thinking after it was let think (`fellBack`), what it thought, up to 60,000 characters (`thinking`), what it considered, as the clues of the first game, with what the rules said of them and how their rehearsals went, and the lines of the second, with what the rules said of them, in the second game the judgment that a player with a term wrote before its line or its vote, the other term closest to its own and which of the two the lines fit (`judgment`), and its reason) or why there was none, and whether the answer came too late to be of use (`late`). It has a limit of 1 MB of its own, which the thinking of a long game needs; past it, the log keeps no more and says so (`truncated`). The notes from before the thinking was kept say that the model was not let think (migration 28). A game that no AI played in has none, and an answer that comes after the end of its game goes into no log.
- **Who was who**: `game_players` links each player ID in the game to an account, for everyone with an account who played in it, those who left included, and one who left and came back under both IDs, each row naming the game (migration 24); and, since migration 27, for whoever took part in it without playing (`GameModule.contributors`): the setter who gave the words of a game of the second game, and the member who gave the chair's own words of a game of the first, if they didn't play, who are counted among no players but may watch it again ([Replays](#replays)). Guests have no row. An account's ID never changes, and a deleted account's is never given out again, so a new username changes nothing here.
- **Counted again.** What the record of a game that finished keeps of how it came out, who won and how (`winner`, `reason`), what the records keep of it, each account's result, place, points, verdict, detail and titles ([Accounts](#accounts), [Titles](#titles)), each AI player's result, place and feats ([AI players](#ai-players)), and of a match that ran its course, each account's place, total and title ([Matches](#matches)), is a count under the rules of the game, from the moves in the log and how the game began: the moves are facts, what they count for is the rules'. So the records are kept for the pages, which must be quick, as a count under the rules of today, and when a game's rules change (`GameModule.rulesVersion`), the server counts every kept game of that game again as it starts (`server/src/store/recount.ts`), in one transaction, after a snapshot, the one from before a migration this start or one of its own (`-before-recount`), and says so (`records_recounted`); the version counted under is in `settings` (`rules_counted:<game>`). The game counts a kept game as it works out its replay, from how it began and its log, with who was who (`GameModule.recount`); the matches are added up here as the match adds them up, by each player's number in the match. A record that can't be counted again, or that disagrees with the log on a fact such as who played where, stops the server, as a migration that fails does, with the database as it was. The check of the data holds every record against the count ([Data](#data)).
- **Deleting** an account marks the player IDs it had in the games it played in, in each log's `deleted`, in the same transaction, and keeps what it said, as nobody's, as the rest of the log is: nothing links the IDs to the account any more, and the mark lets whoever reads the records tell what deleted accounts said from what guests said, as for data that is made public. Then its rows in `game_players` go with it ([Replays](#replays)). An account deleted during a game counts as having played no more, and its player IDs are marked as the game is kept, as are the IDs of one deleted before what the groups said after the end is kept. The log still names the player IDs the account had, and a replay shows it as a deleted player.

The game says what its messages keep: for the first game, every message but choosing a card, as its schema reads it, without the game's ID and with the clue's word as the record keeps it, and a line of the chat as what the player said; of a group's marks, how they stood when it revealed a card, when a turn ended and when the game ended ([games/keywords.md](games/keywords.md#replays)). For the second game, every message of a game, as its schema reads it, without the game's ID and with what the player wrote cleaned as the game keeps it, but taking a place at the table and the setter's words, which come in the waiting room, and a line off the field or after the end (`impostor:say`) as what the player said; and of its own changes (`GameModule.logChanges`), every vote once revealed, every line whose time ran out, every report settled, with everyone's verdict, every player who went out, how and in which round, marked when the chair removed them, every guess of the students' word and the end ([games/impostor.md](games/impostor.md#who-sees-what)). Its records name the role as both the side and the role, the verdict how the player's game went (`alive`, `voted_out` or `violation`; whoever left has no record), and its detail the round they went out in, the rounds they lasted, their votes, those that hit someone not a student and those that sent a student out, their abstentions, the votes and lines whose time ran out, the reports against them, by them and by them that failed, and how their guess of the students' word went ([games/impostor.md](games/impostor.md#points)).

## Matches

A match plays a set number of games, scores every player in each, and ranks them by total. `MatchRules` (`shared/src/match.ts`), given at creation: 1 to 10 games (3), or only those that the game takes (`MatchHooks.games`: 3, 5 or 7 for the second game), and the game's own options (`options`), which the game checks (`MatchHooks.options`, else `bad_match`): for the first game, groups `fixed` or `switch`, made `random` by the server or by `choose` of the players ([games/keywords.md](games/keywords.md#matches)). The room keeps the match (`server/src/core/match.ts`); the game says who is in each of its games through `GameModule.match` ([games/keywords.md](games/keywords.md#matches), [games/impostor.md](games/impostor.md#matches)), and each of its games scores as in any game (`GameModule.score`). A game without `match` plays no match: its room offers none, and the server refuses one (`bad_match`). A withdrawn game isn't one of the match's, nor is one that its game counts for nothing (`GameModule.scoresNothing`), as one of the second game in which the chair removed a player: the match plays it again. Settings are locked once a game has been scored. After the last scored game, the players still in the room are ranked by total, ties sharing a place: the highest total gets the Best Paper Award, and with three or more ranked, the lowest gets Academic Trash, `black_hole` in the code and the database. Ending early ranks as they stand, without titles. Each ranked account keeps the match in `match_records`, with its place, total and how many were ranked, and the title it was awarded in `titles` (`RecordStore` and `TitleStore` in `server/src/store/records.ts`).

A game may ask more of its matches through the same hooks: that they award no titles (`MatchHooks.titles`), as the second game's don't in its beta, and then neither the records nor their count again give any; that the table shows no points of a game in progress (`live`), where they would tell too much; that a game of a match draws only words that the match hasn't had (`fresh`); and that a match ends with its chair (`chairBound`), as one whose words the chair sets: once a game of it has started, the chair passing to someone else ends it early, at once in the waiting room or after the game in progress, which counts; the view says while this is so (`MatchView.chairBound`), and the client asks the chair before they hand the chair on or leave ([games/impostor.md](games/impostor.md#matches)).

**Numbers in the match.** The match gives everyone who plays in it a number, from 1 in the order they enter it, guests and accounts alike, and the log of each of its games keeps everyone's number by player ID (`match.numbers`), and each line of the match's view carries it (`StandingView.number`), so that the match can be added up again from its games whoever has left or deleted their account since: a deleted account's number stays, and the others' places and totals stand. A guest who logs in to an account keeps the number; only when the account played in the match before, left, came back as a guest and logged in again do two lines join, the guest's number going into the account's, which the logs note (`match.merged`). The games of a match are those with its ID on their record (`match_id` in `replays`).

## Ratings

After a game that finished by itself as one that its game says may be rated (`GameModule.ratings` and `GameModule.rated`: for the first game, one that a group won; for the second, one that a side won), every person with a result in it ([Accounts](#accounts)), guests too, is asked on a card under the result how its words were (`RatingCard.vue`, in both games): the first game asks of the words of its board, the second of its pair of terms, which the card names. The options are the same in both (`RATINGS` in `shared/src/room.ts`): good, too hard, too easy and something wrong (`good`, `hard`, `easy`, `problem`). A player chooses one with `room:rate`, which names the game, so that a rating sent late can't land on the next game, and may change it for as long as the room shows the game. Until they choose one, the card's round close button dismisses the question, which is kept as no rating, null, can't be taken back and takes the card away (`Room.rate`); once they have, the card says that it was noted, and the close button only closes the card on that page, keeping the rating and sending nothing, so that a reload shows it again. A game that was withdrawn, cut short or that nobody won, and an AI player, are asked nothing (`cannot_rate`). "Say something" on the card opens the feedback form with the game attached ([Feedback](#feedback)).

**Kept** in `ratings` (migration 27, `RatingStore` in `server/src/store/ratings.ts`), by the socket layer once the room took it: one row for each player of a kept game, by the game's ID, the game and the player ID they had in it, with the rating or null and when it was given, a later rating taking the place of an earlier one, and pointing at the record of the game (`ON DELETE CASCADE`, [Game records](#game-records)). Nothing is kept while the database is full. The check of the data finds ratings that aren't one of their game's, and ratings of a game that didn't finish ([Data](#data)).

**What they are for:** the second game draws its pairs by them, counting them anew for every draw and keeping nothing of the count (`RatingStore.pairRecords`): good ratings weigh a pair up, and a pair that `PAIR_PROBLEMS` people (2) or more rated as something wrong is drawn no more ([Games](#games)). An account's page counts the games of the second game whose words it set and the good ratings players gave them, and its own page lists the latest of them, each with its good ratings and all its ratings ([Accounts](#accounts)). The first game's ratings are kept for whoever reads the records, and nothing on the site counts them yet.

## Guessing the AI

After a game of the second game with AI players at the table and at least 3 people (`AGENT_GUESS_PEOPLE` in `server/src/games/impostor/rules.ts`), in a game that showed the players by number and nobody's name (the `anonymous` setting, [games/impostor.md](games/impostor.md#numbers)), each person who played in it is asked on a sheet which numbers were AI (`AgentGuess.vue`), before the end shows them whose number was whose ([games/impostor.md](games/impostor.md#ai-players)). They choose as many numbers as there were AI players at most, or skip, and send it with `room:guessAgents`, which names the game. The game takes it once (`GameModule.guessAgents`), refusing it from whoever has no guess to make (`cannot_guess`) and a guess of numbers that aren't at the table, repeated or too many (`bad_request`), and then shows them the answer; until then, the [replay](#replays) of the game, which shows who everyone was, is withheld from them (`GameModule.guessing`, `Room.guessing`). The first game takes no guesses. **Kept** in `ai_guesses` (migration 27, `RatingStore`), by the socket layer: one row for each player of a kept game, by the game's ID, the game and the player ID, with the numbers they guessed as a JSON array, in order, or null for a skip, and when, pointing at the record of the game (`ON DELETE CASCADE`); nothing while the database is full. The check of the data finds guesses that aren't in their game's shape (`GameShapes.guess`), and guesses of a game that didn't finish or had no AI player in it. They are kept for whoever reads the records; nothing on the site counts them.

## Limits and housekeeping

- **Rate:** about 10 messages a second per connection, bursts of 20; a message is at most 16 KB.
- **Per address:** 5 rooms a minute (`ROOMS_PER_MINUTE`), 20 codes a minute that belong to no room (past them, public rooms are still found), 3 pieces of feedback every 10 minutes (`FEEDBACK_PER_10_MINUTES`), 100 connections open at once (`MAX_CONNECTIONS_PER_ADDRESS`), counted from Engine.IO's handshake to the connection's end whether or not it comes to Socket.IO, past which a new one is refused with 403, which nothing else Engine.IO refuses gets, so the page knows the refusal by it: it says that the network has too many connections open, and tries again by itself every 30 to 60 seconds, as when the server is busy. Behind a reverse proxy, `TRUST_PROXY` takes the address from `X-Forwarded-For`. **Per account:** 5 reports an hour, 30 friend requests a day, 30 searches for an account by username an hour, one invitation a minute to the same friend ([Friends](#friends)), 100 likes a day ([Public profiles](#public-profiles)).
- **Busy:** with more than `BUSY_CONNECTIONS` connections (10,000) or `BUSY_MEMORY_MB` of memory in use, the heap and what Node holds outside it (90% of what the process may use, the system's limit for it or else the machine's memory, or of the heap's limit if that is less, as it is unless the process is kept very small: the heap runs out, and the process with it, before the memory it may use is full, so a `BUSY_MEMORY_MB` above the heap's limit is logged as `busy_memory_above_heap_limit` and hardly ever reached), the server is busy. The resident memory that `/status.json` shows runs higher, and hardly ever comes down once it has gone up, which is why it isn't the measure: a server judged by it would stay busy for good after one spike. It takes no new connection but one whose handshake brings a member back to the seat the connection would take, by its account or by the seat its browser took as a guest, on 3 connections at most, or a screen back to its room, where the room would put one up for it ([The handshake and reconnecting](#the-handshake-and-reconnecting)); a connection it let through so that the room has no place for after all is closed, as is a screen's that a returning screen takes the place of. It makes no new room, answering both with `server_busy`; the page says that the server is a little busy and to come back in a few minutes, in place of whatever it was waiting for, and tries again by itself every 30 to 60 seconds. The rooms, their games and the open connections go on, and the server takes newcomers again once both numbers are below 90% of their limits. It never shuts itself down, which would only finish what an attacker started. The log says when it starts and stops being busy (`busy_started`, `busy_ended`), and `/status.json` whether it is ([Status](#status)).
- **What was refused:** each refusal by a limit, with `rate_limited` or a `*_limited` code, the room's limit on what one member adds to the log of a game included, for the connections of one address, or while busy, is counted, and once a minute each limit that refused anything gets one `limited` line in the log, with `level: "warn"`: the limit, how many times it refused, and from how many addresses, IPv6 by /64, but never which. The cooldowns between two reactions and between two invitations to the same friend aren't counted.
- **In one place:** `SocketLimits` in `server/src/core/socket.ts`, `RoomLimits` in `server/src/core/rooms.ts`, the connections and being busy in `server/src/core/load.ts`, the line of the minute in `server/src/core/refusals.ts`. 30 players per room, 2000 rooms per server.
- **The sweep,** once a minute, closes rooms with nobody online for 30 minutes or nothing happening for 6 hours, and drops members offline for 10 minutes from waiting rooms.
- **Stopping:** every connection hears `room:closed` with `restart`, then the database closes; after 5 seconds the process ends anyway (`stop_timed_out`). A wrong setting, library or database stops the server before it listens (`startup_failed`, `listen_failed`).

## HTTP

Files under `/assets/` carry a content hash and are cached for good; everything else is `no-cache`. Every response carries a Content Security Policy (`script-src 'self'`, no framing) and `nosniff`.

The server waits 20 seconds at most for a request's headers and 30 for the whole request, keeps an idle connection open for its next request for 5 seconds, and refuses headers of more than 16 KB with 431 (`HTTP_LIMITS` in `server/src/server.ts`), so that a client that sends a request a byte at a time can't hold a connection for long. None of it cuts a WebSocket, nor a long poll while the server holds its answer.

## Search engines and link previews

Search engines, and chat apps that preview a link, read the page as the server sends it, before or without its script, and can't tell which language the reader reads. So `index.html` has, in both languages and English first, the home page's title and description, the Open Graph and Twitter tags of a preview, with the picture `/share.png`, and inside `#app` an introduction to the game, which the app replaces as it starts. The build writes them from the locale files (`client/src/core/site.ts`); as it runs, the app gives each page its own title and description in the interface's language (`client/src/core/head.ts`).

`/?lang=en` and `/?lang=zh` open the home page in that language, as choosing it on the language gate does, and remember the choice. The server sends them as copies of `index.html` whose head is in that language alone, `index.en.html` and `index.zh.html`, which the build writes beside it, so that a link to either shows its preview in that language: the English one with the picture `/share-en.png`, the Chinese one with the picture in both languages. Any other query, and any other page, gets `index.html`. The gate's choices are links to them, so that a search engine, which finds the gate as every first visit does, can follow them. A player's page asks search engines not to list it, and `robots.txt` keeps them out of rooms, the account pages, the API, avatars and Socket.IO.

With `SITE_URL` set at build time ([development.md](development.md#environment-variables)), the picture's address is a full one, which some apps need, the home page names its address in its language as canonical, and `sitemap.xml` lists the home page in each language and the gate, each naming the others as its alternates. Without it, the page names no address of its own, and there is no sitemap.

## Data

- **`DATA_DIR`** ([development.md](development.md)) holds `reviewer2.db`, `snapshots/` and `avatars/`. Without it, the database is in memory, gone at every stop.
- **SQLite** through `node:sqlite`, synchronous; WAL mode, a 5-second wait on a lock, secure delete.
- **Migrations:** `PRAGMA user_version` and `server/src/store/migrations.ts`, run on start in one transaction, after a snapshot. The records are counted again the same way when a game's rules change ([Game records](#game-records)).
- **Snapshots** every hour into `snapshots/`, the last three kept, and one before each migration, the latest of each version kept for 7 days, and one before each recount of the records, unless the one from before a migration this start serves, the latest kept for 7 days.
- **The check.** `admin.cjs data check` ([development.md](development.md#accounts-and-email)) holds every row against the rules that the code takes for granted of the data and that the schema can't enforce (`server/src/store/check.ts`): every account's handle, key, avatar and last room setup, field by field; every game's log and AI log in the newest format, how it began in its game's shape, and every finished game's replay worked out from it; every record of a game, match and title against what its game counts again from the record of the game, every record's detail and every AI play in its game's shape, and every AI play against what its game counts again, the game judging its own shapes (`GameModule.shapes`), so that the check names no game; every title one that some game or a match brings (`knownTitles()`, [Titles](#titles)); every rating one of its game's, of a game that finished, and every guess of the AI players in its game's shape, of a game that finished with AI players in it ([Ratings](#ratings), [Guessing the AI](#guessing-the-ai)); every adoption of a game's words of a kind there is, in its shape, of a game the server plays, and of the game they came from while it is kept, with both sentences ([Content contributions](#content-contributions)); the ways feedback may be; the contributions from GitHub, their kind, username and advisory, and that no issue is a player's feedback and a developer's both; what the housekeeping clears; and, where the avatars are, the files that no account shows. It reads alone, names rows by id alone, and is run before a release and after a migration ([the data rules](rules/constraints.md#data)).
- **The disk.** Feedback stops at 10,000 pieces or 50 MB, which `MAX_FEEDBACK` raises together; nothing is deleted to make room, and only what the operator puts in the trash ever goes, 30 days later ([Feedback](#feedback)). Past 1 GB nothing new is kept (`storage_full`). Avatars up to 2 GB.
- **Deleting.** Everything of an account goes with it through foreign keys, its records of games and matches with their titles, its friendships, its likes, given and received, and its rows in `game_players` included; earlier snapshots keep it. The number it had in a match stays in the logs of the match's games, by player ID alone, so that the match adds up again without it ([Matches](#matches)). Its feedback, its contributions among it, which show a deleted player where it signed them ([Feedback contributions](#feedback-contributions)), the words adopted from its games, which name nobody any more ([Content contributions](#content-contributions)), and the reports it sent or got stay, no longer linked to it, and so do the records of the games it played in, the AI's logs among them, which hold the clues, every move by player ID and what it said in the chat, marked as an account's that was deleted, with its ratings of them and its guesses of their AI players, by player ID too ([Ratings](#ratings)), since the others played in them too, but not its name ([Replays](#replays), [Game records](#game-records)).

## Feedback

Players send it from the foot of the home page or a room; `admin.cjs feedback list` shows it. The rules are in `shared/src/feedback.ts`, run on both sides. **Kept:** text, contact, kind (an idea, a new game, a bug or the word lists), version, language, page, time, for a bug only the user agent, the game it is about, and who it is from, in one of three ways ([Feedback contributions](#feedback-contributions)): signed with the account the player was logged in to (`link_profile`), which keeps the account and no name; anonymous, with the account if they were logged in; or a guest's name of their own. The form asks whether to sign the feedback, which it offers first, or to stay anonymous: a player who is logged in signs with the account, and a name that an older page sends along signs with it too and isn't kept; a guest types a name of their own. The form says that what a player writes may become a public GitHub issue, never their contact. **The game it is about:** feedback sent from the card that asks how a game was ([Ratings](#ratings)) carries the game's ID (`gameId` in `meta:feedback`), which the form says goes along with it, and is kept with the game and its ID (`game`, `game_id`, migration 27) when the sender took part in the game that has just ended in their room, as a player or as whoever gave its words (`Room.tookPart`), and the game is kept; otherwise it is kept without one. `feedback list` shows the game, so that the operator can look at its record; the issue's text never names it. Feedback from before also kept a link for the name and whether the player agreed to a public issue, which migration 17 dropped. **Not kept:** address, nickname, token, member key, room code. When full, players are told (`feedback_full`).

**An archive, with a trash.** The feedback is the project's archive of suggestions: no code changes what a player sent, and `server/src/store/archive.test.ts` fails if any is added. The only changes are what players were promised and the operator's notes: **contacts are cleared after 90 days** (`contacts_cleared`), deleting an account unlinks its feedback, and `admin.cjs feedback` records what became of it (migration 9), which `feedback list` shows as a status and a trail: `issue` the GitHub issue it became, with its text and who sent it and never its contact; `resolve` the pull request that resolved it; `close` and `reopen` whether it was closed without being adopted, which adopted feedback can't be; `adopt` makes an issue that isn't closed a contribution ([Feedback contributions](#feedback-contributions)), and `describe` rewrites what the contribution says. The status is the first of these that holds: in the trash, closed, resolved, which is adopted, whether a pull request was recorded or not, an issue, which is published as an issue or recorded as resolved by a pull request without being adopted, or new. The list writes out what the feedback came to, such as "Issue #42", "Resolved · PR #72 · issue #42", or "Issue #42 · PR #72" for feedback whose pull request was recorded but which still waits to be adopted. Its views (`--status`) are all, the trash included until it is purged, open, which is the new feedback that nobody has dealt with yet and the default, and each other status alone, issue, resolved, closed and trash; none overlaps another but all. Each lists all of its feedback, the newest first, for people to read or, with `--json`, for scripts. The issue's text comes from `feedback draft`, which writes its title and body from a template, with the player's text and who sent it alone, as the form promises: the username of the account that signed it as it is then, or a deleted player once it is gone, a guest's name, or an anonymous player, and, for a bug, the version of the page it came from and the names and versions of the browser and the system, read from the user agent (`server/src/userAgent.ts`), leaving out a version of the system that browsers hold still, such as Chrome's Android 10, and never a phone's model or the user agent itself, for the operator to create the issue on a machine that reaches GitHub; the server never talks to GitHub. `feedback delete` puts feedback in the trash and `feedback restore` brings it back; the server deletes what has been in the trash for 30 days, at start and every hour, logging only the count (`feedback_purged`). That purge is the one way a row ever goes, and it leaves feedback that was adopted or is a GitHub issue alone, however it got to the trash: adopted feedback can't be deleted, since it is a contribution, nor can feedback that is a GitHub issue, which is public and is closed instead, and feedback in the trash still counts against the limits until it is purged. The table was rebuilt in migration 5, every row copied with its id, so that its kinds are checked in `shared/src/feedback.ts` alone and a new kind needs no migration, and again in migration 27, every row copied with its id and the count that new ids go on from, so that a row names the game it is about by its record, the game and its ID both or neither, forgetting the game rather than the feedback if the record goes (`ON DELETE SET NULL`); besides, migrations only add to it, but for migration 17, which dropped two columns that nothing used any more ([Feedback contributions](#feedback-contributions)). The reports of players are a strict archive: no row is deleted ([Public rooms](#public-rooms)).

## Feedback contributions

The contributions are listed on the home page from the database, and nowhere else in the repository, and come from two places. **From the site:** a row of the feedback that `admin.cjs feedback adopt` adopted, of the kind of the feedback (an idea, a new game, a bug or the word lists). Every adopted piece of feedback is a GitHub issue first, and `adopt` refuses one that isn't; the issue, which links the pull requests that closed it, is its record on GitHub. Adopting records when it was adopted and one sentence in Chinese and one in English on what the player contributed, written by the operator; `feedback describe` rewrites the two, and nothing else of a contribution ever changes (migration 17). **From GitHub:** an issue that a developer opened with one of the repository's forms (`.github/ISSUE_TEMPLATE/`, [maintainers.md](maintainers.md#issues)) and `admin.cjs github adopt` adopted, or, for a security problem reported privately, the advisory published once it was fixed, kept in `github_contributions` (migration 25): the issue's number or the advisory's id, one of the two; its kind, the kinds of feedback and `code`, for what players don't see, checked by the code as the feedback's is (`CONTRIBUTION_KINDS` in `shared/src/contributions.ts`); the username and the id of the author's GitHub account as they were when it was adopted, which the operator reads from GitHub, since the server never talks to it; whether the home page names the author, as they chose on the form; when it was adopted; and the two sentences. Nothing else of the issue is kept: the issue is its record. An issue is a player's feedback or a developer's, never both: `feedback issue` and `github adopt` each refuse the other's, and the check of the data finds one in both tables. The rows are an archive like the feedback (`archive.test.ts`): none is deleted; `github describe` rewrites the sentences, `github anonymous` lists the author anonymously at their request, and `github forget` also drops their username and id. A pull request is no contribution here: GitHub lists those who wrote code among the repository's contributors, which the home page's card says, and nor are the words that players gave in their games, which are kept apart ([Content contributions](#content-contributions)). `shared/src/contributions.ts` has the rules.

`GET /api/contributions` lists them all (`ContributionStore.all()`, `server/src/store/contributions.ts`), the newest adopted first, each with its kind, where it came from, who it is from, the sentences, the issue or the advisory and the month it was adopted, never the text, the contact or an account. Feedback signed with an account (`link_profile`) keeps no name: it is listed by the account as it is now, its username, the handle of its public profile and its avatar, which the home page shows before the name, both opening the account's panel ([Public profiles](#public-profiles)), and once the account is deleted as a deleted player's (`deleted`), by no name, avatar or link. A guest's is listed by the name they left, and anonymous feedback by none; neither holds a trace of an account. An issue from GitHub is listed by its author's GitHub username while they are named, which the home page shows after GitHub's mark in place of an avatar, both leading to the author's GitHub page in a new tab with the arrow of a link that leads off the site ([display rules](rules/display.md#links)); an author listed anonymously is an anonymous player, with no trace of their GitHub account. The home page keeps a column for the avatar on the entries that have one, and what follows the name wraps under itself, in a section for each kind that has any, the code last; the card's title counts the people, those from the site and those from GitHub apart, since one username on both may be two people. An account's page counts its contributions of each kind, anonymous ones too, and its public profile does while its owner shows them; deleting the account unlinks them, and they stay on the home page. A contribution from GitHub counts for no account.

## Content contributions

Players give the word library words in their games: the setter of a game of the second game its pair of terms ([games/impostor.md](games/impostor.md#the-setter)), and the chair of a game of the first the words of their own on its board ([custom words](games/keywords.md#custom-words)). The record of the game keeps them, as it began, with who gave them by player ID ([Game records](#game-records)). The operator may add them to `words/` by hand, as any change to the lists ([words/README.md](../words/README.md)), and then adopt them with `admin.cjs content adopt` ([development.md](development.md#accounts-and-email)), which takes what the game says that the record holds of them (`GameModule.content`): the kind, `pair` or `words` (`CONTENT_KINDS` in `shared/src/contributions.ts`), the words, two of a pair with its field or up to `MAX_CONTENT_WORDS` (25) of the chair's own, and who gave them. It refuses a game that isn't kept, one that holds no words a player gave, and one whose words were adopted already, and takes one sentence in Chinese and one in English on what was adopted, as `feedback adopt` does. Kept in `content_contributions` (migration 27, `ContentStore` in `server/src/store/content.ts`): the kind, the game, the game it came from (`game_id`, which the row outlives, `ON DELETE SET NULL`), the words as JSON, the account that gave them, read from `game_players` by the player ID they had, while it is there (`ON DELETE SET NULL`), whether it is named, when it was adopted and the two sentences. Whether it is named follows what the setter asked for on the form, and the chair's own words are named, unless the operator adopts them `--anonymous`; a row without an account names nobody. `admin.cjs content list` shows them all, the latest first. The rows are an archive, as the contributions from GitHub are (`archive.test.ts`): no command deletes or changes one, and deleting an account only makes its rows name nobody (`ContentStore.forget`), in the transaction that deletes it, before its foreign key unlinks them. Nothing on the site lists them yet: they count for no account and aren't among the [feedback contributions](#feedback-contributions).

## Acknowledgments

`ACKNOWLEDGMENTS.md` holds the maintainers' own thanks, written by hand as they like, in any language, to anyone, with an account or without, and the home page shows it ([Lists of thanks](#lists-of-thanks)). It is a little Markdown, which the page shows as GitHub does: headings, paragraphs, lists, `https://` links, bold and italic ([format](development.md#acknowledgments)). `shared/src/acknowledgments.ts` reads it into blocks of plain text, which the page builds its own elements from, never HTML. It refuses HTML, character references, images, horizontal rules, bare web addresses, links that aren't `https://` and links inside bold or italic text, in CI and on the server; anything else it makes nothing of, such as a numbered list, shows as it is written, which may differ from GitHub.

Until migration 17, an `acknowledgments` table recorded whom the operator thanked, by adopting feedback or by hand, and the file listed every adopted piece of feedback. The migration made the adopted feedback contributions, adopted when its row said, and dropped the table; those thanked by hand are in the file alone.

`SPONSORS.md` thanks the sponsors by name: no amounts, tiers, or whether they give monthly. ## Lists of thanks

The home page shows the feedback contributions, the sponsors and the acknowledgments as three folded cards, the first two with titles that count the people listed, so it asks `GET /api/contributions`, `GET /api/sponsors` and `GET /api/acknowledgments` once, when it shows them, and again when a card that failed to load is opened. The contributions come from the database ([Feedback contributions](#feedback-contributions)); the other two are files. The build bundles both files into the server. With `CONTENT_DIR`, the server shows the copies in that directory instead, so a list changes without a new build or a restart: each request compares the file's modification time, size and inode with those of the copy read last, and the server reads the file again only when they differ, or when it couldn't open or read it the last time, such as for its permissions. A file that is missing, over 64 KiB, not UTF-8 or against the rules leaves the bundled copy in use, and the log says why with `thanks_list_skipped`, once for each new reason. The server never writes to the directory. The same parsers check both files on the server and in CI (`server/src/thanks.test.ts`): `shared/src/acknowledgments.ts` the acknowledgments, `shared/src/lists.ts` and `shared/src/sponsors.ts` the sponsors. Everything in them shows as plain text; links, only `https://`, open in a new tab with `rel="nofollow ugc noopener"`.

## Accounts

Optional: a username and a password, with an avatar, a record of games, titles, the count of its [feedback contributions](#feedback-contributions), a [public profile](#public-profiles), and, if wanted, an email address for resetting a forgotten password, which itself is never kept.

- **Usernames** follow the nickname rules, with at least 2 characters, no reserved names and no guest's name ([Players and identity](#players-and-identity)); `usernameKey()` in `shared/src/accounts.ts` compares them.
- **Passwords:** 8 to 128 characters after NFKC, as scrypt hashes, N = 2^15, r = 8, p = 3 (`server/src/accounts/passwords.ts`). Two hashes at a time, then `busy`.
- **Logins:** a 32-byte secret in a cookie, kept as its SHA-256 (`sessions`). `HttpOnly`, `SameSite=Lax`, `Path=/`, and unless `COOKIE_SECURE=0`, `Secure` with `__Host-`. Ends after 30 days unused, a year in all, or on logout or a password change; its connections then get `account:ended`.
- **Connections.** The handshake reads the cookie; a logged-in connection takes its member key from the account. A guest's seat becomes the account's when the browser logs in and comes back.
- **Records.** At a game's end the room keeps the record of the game first ([Game records](#game-records)), then asks `GameModule.results()` and keeps each account's part in it, which points at the record of the game: the side and the role, which are facts of the game, and what the game counts of it: the result, `won`, `drawn` or `lost`, the place, the detail of its scoring in the game's shape (`detail`, `GameModule.shapes.detail`, migration 26), the verdict and the points ([Academic ranks](#academic-ranks)), with the titles it brought the player ([Titles](#titles)), the streak it brings ([Streaks](#streaks)) and the titles it brings friends ([Friend duos](#friend-duos)). Who won, when the game ended, whether an AI played and which game of a match it was are the record of the game's, which the pages read with the record (`Room.matchGame()`, migration 24). Every count is of one game, since a win means something else in each (`RecordCounts` and `RecordsView`, by game ID): the server sends each game's, and the account page shows one game's record at a time, under a tab for each game, in the games' order, with none for all of them (`GameTabs.vue`, `client/src/core/records.ts`); under the tab of a game in beta, a line says that a big update may clear its records, and that the others stay (`BetaNote.vue`). Then the game's numbers, on small blocks, as the game counts them (`RecordStats.vue`, `StatBlocks.vue`, `GameInfo.recordStats` in `client/src/games/info.ts`). The first game's are six: the games, the share of them won, as a whole percentage rounded down, the share won as a group's PI and as a student, each over how many games, which count every game as the total does, how many matches the account finished, and how many of them it finished first, level with others too; the server still sends the games outside matches and those in matches apart. They are in one line of six where the record's box is wide enough, as on a wide account page, and else four and two, the rates in each role on the second line, as on a phone or in a panel; the box, not the screen, decides, through a container query. The second game's are eleven, three to a line: the games, the share of them won and the share of the account's votes that went to a Reviewer 2 or the PI, over how many votes; the share won as a student, as a Reviewer 2 and as the PI, each over how many games; and the rounds it lasted on average, to one decimal place, the games it went out of for breaking the rules, and the games that finished whose words it set, with the good ratings players gave them ([Ratings](#ratings)); and, as the first game's, the matches it finished and those it finished first. What a game's records add up besides the games and the wins, the game names (`GameModule.recordSums`: for the second game, the votes, hits and rounds of the records' detail, and the records with the verdict `violation`), and the server counts it from the records whenever it is asked for (`RecordStore.sums`, `GameCounts.sums`), as it counts the games whose words the account set, by its row in `game_players` as their setter (`GameCounts.wordsSet`, `RatingStore.setterCounts`); nothing is kept for either. Then that game's latest 20 games, one line each: when it ended, in numbers as 2026.10.14 18:08 in every language, whether it was an ordinary game or which of its match, as "Match 2/3", or, for a game that an AI played in, which is never one of a match, the robot's head and "AI" in their place, which a tap explains: it brought nobody points (`GameRecord.agents`), the role on a chip, in the group's tint in a game of groups and in ink in one where everyone plays alone, what the game made of it: in the first game the decision that the group got, by its short English name in every language ("Oral", "Desk Reject"), and in the second how the player's game went, in the interface's language ("Lasted", "Voted out"), and a round button on the right to watch it again; and the latest 20 matches, each with its games, its place and total, and its title on the right. Then, for an account that has set the words of a game that finished, the latest 20 of those, under "Pairs you set", in the same look: when it ended; a tag with how many of the players who rated it rated it good, of how many rated it, those who dismissed the question left out ("Liked 2/5", or "No ratings"); the words as the setter gave them, in the order the game keeps them, in the second game the students' term first (`GameModule.content`); and the round button to watch it again, which the setter may ([Replays](#replays)). The server reads them from the records of the games and the ratings whenever they are asked for, as it counts them (`RatingStore.setterGames`, `GameRecords.wordsSetRecent`), and sends them to the account alone: its public profile has the counts and no list. The columns of each list line up from line to line where the browser has subgrids. What a line says of its game goes on to a second line where the line has no room for it, rather than being cut short as a match's title is ([rules/display.md](rules/display.md#panels-rows-and-tags)).
- **The last room setup.** As an account makes a room, the server keeps how it set it up (`RoomSetup` in `shared/src/accounts.ts`, `room_setup` as JSON, migrations 19, 24 and 26), by game: the room's language, the fields and whether every game draws them anew, the game's settings as the game took them, the match's rules with the game's own options ([Matches](#matches)), whether the room is public and whether the creator plays; and, for a practice room, the fields and, from a room for the player alone, the role, apart. The owner's summary has it, and the next setup starts from it, as far as it still holds: fields with too few words in the language drop out, a setting that no longer will do is the game's default, as is one that the language counts in other units, such as a clue's length, and a room is public only for an account. A guest's last setup stays in the browser's local storage, where the rules of a match kept before they carried the game's own options are read as if they had. It goes with the account.
- **Games played.** The owner's summary names the games that the account has a [record](#game-records) of, practice games and games with AI players included (`played`, from `game_records`), which the home page reads to offer a game's [tutorial](#the-tutorial) to an account that hasn't played it. Nothing of its own is kept for it.
- **Numbers.** An account's id, from 1 in the order of registration, never given out again, is its number, shown on its own page and its public profile and never a way to look an account up. The first account is the author's (`AUTHOR_ACCOUNT`), which both pages mark.
- **The records notice.** Registering takes the player's agreement to the notice on how games are recorded, which the form shows with a box under it to tick (`privacy.records` in the locale files, [Game records](#game-records)); the request says which version of the notice the player agreed to (`consent`), the server refuses another (`consent_required`), and the account keeps the version and the time (`consent_version`, `consented_at`, migration 23). The version is of what the notice says (`RECORDS_NOTICE_VERSION` in `shared/src/accounts.ts`), not of the software: it goes up only when what is recorded or what it is used for changes in substance, so that the accounts that agreed to an earlier notice can be told apart and asked again. The accounts from before migration 23 agreed to the first version, as the maintainers confirmed with their players, at the time of the migration. A guest, who agrees to nothing, is told in a line on the forms that make and join a room that the games are recorded (`privacy.guestNotice`).

## Friends

Accounts only; guests see none of it. `shared/src/friends.ts` has the types, the limits and the error codes.

- **Search.** The account page finds someone by their whole username (`friends:find`), compared as names are, which answers with the handle of their profile and the username, or `no_such_account`; nothing finds an account by a part of a name or by its number. A link to a page, pasted with any text around it (`handleInLink` in `shared/src/accounts.ts`), is read as the page it leads to (`GET /api/profile/<handle>`), with no search. Either opens the other's panel (`ProfilePanel.vue`), as a tap on their avatar does: a brief card, under it what the account may do by how the two stand, and last the whole page. The owner's account page says that others find it so.
- **By how two stand.** A room's player panel, the search's panel and a public page offer the same (`FriendActions.vue`, by `standingOf` in `client/src/core/friends.ts` over the viewer's own friends list): a stranger is asked in a sheet with a line for them (`BefriendSheet.vue`); whoever was asked already, a word that the request went; whoever asked the account, their line and Accept and Decline; a friend, a name of the account's own (`AliasSheet.vue`) and the end of the friendship, after asking first (`UnfriendSheet.vue`), as from the friend's card on the account page. A page has them as small buttons beside the like, with the line of a request above them. The sheets lie over the panel or the page.
- **Requests.** An account asks another by username (`friends:request`), from the search's panel or from their public page, or a player in the same room by their ID from the player's panel, if both have accounts, with a line for them if it likes (`note`): one line of at most 50 characters, cleaned as a line of the chat is and otherwise as written (`checkFriendNote` in `shared/src/friends.ts`). The line goes to the account asked alone, on its account page, and is deleted from the database once the request is answered, accepted or declined, or withdrawn; a request asked anew may have a line of its own. The other side accepts or declines on their account page, or in the panel or on the page of whoever asked; asking someone who has asked already accepts theirs. Either side ends a friendship (`friends:remove`), which also takes back a request. Every change tells both sides' connections `friends:changed`, and so do a new username or avatar and the deletion of an account, to everyone whose page names it.
- **Limits** (`FRIEND_LIMITS`): 100 friends; 20 requests open per sender and 50 waiting per account; 30 requests a day per account, counted before a username is looked up, so that trying names costs as much as asking, and for a player in the room only when a request goes out; 30 searches an hour per account (`findsPerHour`, `friend_find_limited`), counted before the name is looked up, so that a name that finds nobody costs as much as one that finds someone, and none for a link, which leads to a page that anyone with the link may open anyway; after a decline, whoever was declined waits 7 days before asking again, while whoever declined may ask at any time. The other friends messages answer a name that is no account's as they answer a stranger's.
- **Names for friends.** An account may give each friend a name of its own (`friends:alias`, `checkAlias` in `shared/src/friends.ts`), for itself alone, as a phone's contacts have: one line of at most 20 characters, cleaned as a nickname is, which an empty one takes away. The friend isn't told, and nobody else is sent it: it goes in the account's own friends list (`FriendView.alias`) and with a friend's invitations to it (`InvitationView.from.alias`). The account's pages call the friend by it wherever they name them, in place of the username, as a phone's contacts do: on the account page and where the account invites friends, in a room and its games, in replays, among the feedback contributions and among those who liked the account's page (`nameOf` in `client/src/core/names.ts`). A friend's panel, their whole page, a shared link to it and the questions before removing, reporting or parting from them put the username after it in small grey type, since such a name may be anyone's. A room's big screen, which the whole room sees, keeps to usernames, whoever is logged in on it, and a default avatar is drawn from the username all the same. The client reads the names from the friends list as each connection of an account is made and on every `friends:changed`, so that a new name shows at once; the server never puts them into a room's view.
- **Presence.** `friends:list` says of each friend whether they are online, every tab and device counting as one person, and which room they are in: with its code if the room is public, so that the page offers a Join button, or if the account has a seat there too, and without it if the room is private, which only an invitation leads into. Nobody but a friend learns this, through any message or API; requests show the username and avatar alone. The account page shows it on each friend's card: a green dot on the avatar of a friend who is online, the whole card faded for one who isn't, and on the name's line the way into the room, "Join room" for a public room and "Ask to join room" for a private one, never the words of where they are. A profile and a panel show nobody's presence.
- **Friends playing.** The home page, for an account, lists the rooms that its friends are in and it isn't (`friends:rooms`, `FriendRoomView`): a row a room, with the friends in it, by the account's names for them, and whether a game is on, and no row while no friend is in a room. The list is asked for as the page opens, on every connection, on `friends:changed` and when the page comes back into sight. A public room has its Join link; a private one, still without its code, an Ask to join button, which asks the first friend in the row, as the button on a friend's card on the account page asks that friend.
- **Invitations.** A member with an account invites a friend into their room (`friends:invite`), online or not, from the start bar at the top of the waiting room, beside the start button for the chair, or from the room menu during a game and while a finished match's ranking stands in the waiting room, once a minute for the same friend, unless the chair has removed the friend from it. The sheet lists every friend who isn't in the room, those online first, with the friends list's green dot, and those offline after them, faded, whose button says that they will see the invitation once online. Every connection of the friend hears `friends:invited`, with the inviter, the room's code and ID and how long the invitation stands, and a connection that comes while it stands hears it too. `room:join` with the `invitation` in place of the code lets the friend in, into a private room too, as a newcomer like any other: a removal by the chair and the account requirement of a public room keep them out as they would anyone. An invitation is used up when the friend comes into the room, by it or by the code, and forgotten when they ignore it (`friends:ignore`); it lapses after 10 minutes, when the inviter leaves, when the room closes or when the two part (`invitation_expired`). One that lapses by its age ends on a timer, as it lapses; one that no longer stands for another reason is found by the sweep. However an invitation ends, every connection of the friend hears `friends:uninvited`, so that none of their pages shows it on. The inviter's own view of the room alone lists the friends whom they invited and who haven't come, while the invitations stand, the oldest first (`RoomView.invited`), and gets the room again as one ends: the start bar shows them as avatars beside its line, as someone the room waits for, and one who comes in in their own colors for a moment, the dots stilled, before they go; the sheet says "Invited" for each. Whoever has a seat in the room comes back by the code, with a lapsed invitation in hand or not. Invitations live in memory and are never kept.
- **Asking to be let in.** An account asks a friend who is in a room to be let in (`friends:ask`), and learns nothing of the room by asking. Every connection of the friend hears `friends:asked` (`JoinAskView`), with the account, by the friend's name for it, the room's ID, which the friend's room page matches to show it, and how long it stands, and a connection that comes while it stands hears it too. The friend answers with an invitation (`friends:invite`), which the account then follows as any other, or ignores it (`friends:dismiss`); the account isn't told which. A request ends when it is answered so, when the account comes into the room, and after 10 minutes (`JOIN_ASK_MS`), when the friend leaves the room, when the room closes or when the two part. However it ends, at once or found by the sweep, every connection of the friend hears `friends:unasked`, and every connection of the account `friends:changed`, on which its pages offer to ask again; while it stands, the friend's card and the row say so (`FriendView.asked`). One request stands at a time to the same friend (`join_ask_pending`), and an account sends at most 10 an hour (`JOIN_ASKS_PER_HOUR`, `join_ask_limited`), counted only for those that go out. Nobody asks into a room they are in already (`already_in_room`), nor one that the chair removed them from (`removed`, `removed_recently`). Requests live in memory and are never kept.
- **Data.** The `friendships` table (migration 8): one row per pair, whichever side asked, with its status and when it was asked and answered, and (migration 16) the line of a request that is open and each side's name for the other. A friendship that is removed is deleted, its names with it, and a declined request is deleted once its wait is over; an account's rows go with it.

## Friend duos

What two friends have played together, and five titles for the friends who stand out (`shared/src/duos.ts`). Two accounts were teammates in a game when both have it on their records on the same side, and opponents when on different sides; each game is counted apart (by game ID), and every game of it on both records counts, in a match or not, from before the two were friends too, but a game that brought nobody points, as one that an AI played in ([AI players](#ai-players)) or one that the chair removed a player from in the second game (`scores_nothing`, [Game records](#game-records)). Only friends count: a request counts for nothing, and the counts go when the friendship ends and come back when it is made again.

- **Counts.** For each friend and game: the games won and lost on the same side, a draw being neither, and the games on different sides, with those in which the account placed above the friend and those in which the friend placed above it (a lower `place`).
- **Titles.** In each game, each is held by the friend with the most of one count, from three on, and friends level at the top share it: Co-First Author, the most games won together; Rejected Together, the most lost together; Your Reviewer 2, the most won against the account; Frequent Submitter, the most lost to it; Rival Reviewer, the most played against it. Each account has its own: Ann's Co-First Author may be Bob while Bob's is Cat.
- **Who sees them.** The account alone. Its friends list carries each friend's counts and titles in each game (`FriendView.duo`) and sums up who holds which, and a friend's public profile carries what the two have played, for that friend alone (`ProfileView.duo`). When a game ends, the snapshot that ends it tells each account player of the titles that the game brought friends who played in it, who didn't hold them before (`RoomView.duos`); nobody else in the room is told, and the screens nothing.
- **Data.** Nothing new is kept. One query counts every friend's games from `game_records`, by game, finding the others in each game by the index on the game (migration 13), whenever the friends list or a profile asks, and once for each account player with a friend in a game that ends. A deleted account's records go with it, and its counts with them.

## Public profiles

Every account has a public page, `/p/<handle>`, which anyone may open, with or without an account. The handle (`accounts.handle`, migration 11) is 12 hexadecimal digits drawn at random when the account is created, never changed and never reused, so that a link outlives a new username and nobody can count through the accounts by their numbers. Rooms, friend lists, requests and the list of likers carry it (`PlayerView.handle`, `FriendView.handle`, `LikerView.handle`), so that every way to a profile uses the same key.

- **The way to a profile:** a tap on an avatar opens a panel over the page, wherever the avatar is, so that nobody leaves a game or a page to look. In a room, the player's panel (`PlayerPanel.vue`): for an account, a brief card with the avatar, rank, number, day of registration and titles, and the whole page as a sheet of its own height over the panel, which it hides meanwhile, at most as tall as a sheet may be, past which it scrolls, with a round button back to it; for the viewer, their own card with the way to their account page, where they change it, and their whole page as others see it; for an AI player, its own page ([AI players](#ai-players)); for a guest, the avatar under the title that names them. Under the card, what the viewer may do with the player: what friends do, as the page itself offers it ([Friends](#friends)), the chair's actions, a report. Outside a room, on the account page and the home page, an account's panel (`ProfilePanel.vue`, one for the whole site, over whichever page opened it) is the same without what only a room has, and the friend search opens it too for the account it finds, as does an account among the feedback contributions on the home page, by its avatar or its username; elsewhere the names beside avatars are plain text. The page itself, `/p/<handle>`, is where a shared link leads, and nothing on the site leads there: the account page opens its owner's own in the panel. A page reached from another on the site has a round button back to it before its title, on a bar that stays at the top as the page scrolls while the masthead scrolls away ([display rules](rules/display.md#layout)), and one opened on its own, as from a shared link, has none: the wordmark leads home.
- **Shown to everyone:** username, avatar, rank, number, the day of registration, titles, the streak titles among them ([Streaks](#streaks)), the link and the line the owner wrote, and how many accounts like the page.
- **Shown unless the owner turns it off** (`show_record`, `show_thanks`; on for a new account, which the owner may turn off; accounts from before they were on keep what they chose): the record as counts, one game at a time under the same tabs and on the same blocks as on the account page, the rates in each role among them and, for the second game, the games whose words the account set with their good ratings (`ProfileView.record`, [Accounts](#accounts)), and the feedback contributions as counts ([Feedback contributions](#feedback-contributions)). The points, the state of the email address, the friends and the games themselves never show.
- **The link** keeps the rules of a web link of a player (`checkWebLink` in `shared/src/feedback.ts`), which the lists of thanks take too: `https://` only, no user name, at most 200 characters. The page shows it as the address it is, opening in a new tab with `rel="nofollow ugc noopener"`. **The line** has at most 80 characters, cleaned as a contact is (`checkBio` in `shared/src/accounts.ts`), and is shown as text, never as markup. Both are optional; `POST /api/account/profile` sets them with the two choices.
- **Likes** (`likes`, migration 11). An account likes a page once and may take it back, never its own (`self_like`), 100 a day (`like_limited`). The count is public; who likes a page is shown to its owner alone (`GET /api/account/likers`), the latest 100 of them (`LIKERS_SHOWN`), with whether each is a friend, so that the owner may ask the others. The rows go with either account.
- **Requests waiting.** The owner's summary counts the friend requests waiting for an answer (`AccountSummary.requests`), for the badge on the home page and the account page; the page asks again on `friends:changed`.
- **The operator** clears a link and a line that break the rules with `admin.cjs profile clear <username> [--ban]`, which with `--ban` bars the account from writing them again (`profile_banned`; `profile allow` lifts it), and looks them over with `profile list` ([development.md](development.md#accounts-and-email)).

## Titles

An account keeps the titles that matches award ([Matches](#matches)) and those that games bring, such as Forgot to Submit for a PI who gives no clue in time, Deadline Hero for one whose last-second clue the students follow to the letter, and the Instant Desk Reject for a group whose first card is Reviewer 2 ([games/keywords.md](games/keywords.md#titles)), each as often as it was won, and its pages show each with the count and the game (`TitleCount`), the first game's alone for now (`TITLES_GAME` in `client/src/core/records.ts`), since the second game, in its beta, brings none ([games/impostor.md](games/impostor.md#beta)). The titles there are, `knownTitles()` in `server/src/core/game.ts`, are the matches' (`MATCH_TITLES` in `shared/src/accounts.ts`) and those that each game declares (`GameModule.titles`, such as `KEYWORDS_TITLES`), and a test (`server/src/games/index.test.ts`) makes sure that no two games declare the same ID and that none declares a match's. A game names them in `PlayerResult.titles`, each with the turn it came in, and they go with the record, in its transaction: a game that goes on no record, withdrawn or played as a guest, brings none, nor does a game that an AI played in ([AI players](#ai-players)) or one that its game counts for nothing (`GameModule.scoresNothing`, [Games](#games)), and a turn of a game brings an account a title once (`titles_game`, migration 14). Each title names the game that its match or its game was of (migration 23), and points at the record of the game or the match it goes with, by the account and the game or the match (migration 24): a match awards an account one title, and the time of an award is the time the game or the match ended. The table no longer fixes the titles with a CHECK: `TitleStore` refuses one that isn't in the code, and the check of the data a game's title that its game doesn't declare. The titles are counted again with the records when a game's rules change ([Game records](#game-records)).

Every title that a page shows opens, at a tap, a sheet that says what it is and how it is won (`TitleInfo.vue`, `client/src/core/titles.ts`): the titles of matches and of games, a game's saying which game brings it, the streaks, on the account page as the longest on the record and at the end of a game as the run so far, the feedback contributions, the author's badge, the decision of each game, on the record and in its letter, the mark of a game on the record that an AI played in, and the [friend titles](#friend-duos). The academic rank opens its ladder instead. Two places show a title that opens nothing: a screen, which nobody taps, shows them as text, and the rank beside a name in a room's list of players, where the avatar beside it opens the player's panel, with the rank and the titles on its card. What each says is in the locale files.

## Academic ranks

Shown only; they change nothing in the game. Every game that ends by itself is scored as its game scores it (`GameModule.score`, [Games](#games)), as a match scores it too ([games/keywords.md](games/keywords.md#matches)), in a match or not, and each account player's points go on their `game_records` row (migration 8), counted again when the rules change ([Game records](#game-records)). The snapshot that ends such a game carries the points of everyone in the room who played in it, guests too, with the game's detail of where they came from (`RoomView.points`), which the game shows as it ends ([games/keywords.md](games/keywords.md#points-as-they-come), [games/impostor.md](games/impostor.md#points)); every snapshot of a game says whether an AI has played in it, so that it brings no points (`RoomView.agentsPlayed`). A withdrawn game counts for nothing, as does one that its game counts for nothing (`GameModule.scoresNothing`), and a game is recorded once per account. The total holds a rank (`shared/src/ranks.ts`), thirteen of them: kindergartner from 0, primary school pupil from 30, middle school student from 80, high school student from 150, undergraduate from 300, master's student from 500, PhD student from 800, postdoc from 1200, lecturer from 1800, associate professor from 2500, professor from 4000, academician from 6000, and Reviewer 2 from 10000, the top, which the account page says has no next rank. The thresholds were set under the scoring before the PI's stakes, when a wrong card cost only the student who revealed it: a regular player, four evenings a week, made about 90 points a week, so primary school came in the first day or two, an undergraduate after about three weeks, a professor after about ten months and Reviewer 2 after about two years. Since every student pays for every wrong card and the PI pays more, a game gives less, and the ranks come slower; the thresholds stay as they were until play shows how much. A change of the table ranks every account by the new one at once. The rank travels with the player in every snapshot (`PlayerView.rank`), is read again when a game ends, when the account changes and at every sweep, and the account page shows the total and the way to the next rank. The rank on the account page and on a [public profile](#public-profiles) opens the ladder of every rank with its points, the player's own marked (`RankLadder.vue`); the public profile's ladder marks the rank alone, since the points never show there.

The rank is the sum of the points of every game on the account, whichever game they come from: a new game calibrates what a game gives to about what the first one gives, so that no game becomes the place to farm points.

## Streaks

How many games in a row an account has won, and lost, at most (`shared/src/streaks.ts`). They are counted for each game apart (`AccountSummary.streaks` and `ProfileView.streaks`, by game ID), over every game of it on the record, in a match or not, in the order the games ended, counting only games that brought points, which those that an AI played in don't ([AI players](#ai-players)), nor some of the second game (`scores_nothing`, [Game records](#game-records)), where a draw ends a run of either kind: a withdrawn game has no row, watching is no game, and a guest has no record. Nothing of them is kept: the account page, the public profile and the end of a game count them from the record whenever they are asked for (`streaksOf` in `server/src/store/records.ts`), the end of a game in the transaction that keeps the record, which takes a moment for the longest record. A `streaks` table kept them from migration 10 to migration 23, which dropped it after holding every row against the count, since every game on the record says how it went for the player and in which order it came, and a count kept beside the records could only fall behind them. The end of a game counts the streak in that game alone, and the pages show the first game's.

A streak of three games or more is a title, named with the number in words (`shared/src/numbers.ts`), never a digit: Three Submissions, Three Acceptances, and Three Submissions, Three Rejections, with the number in Chinese characters in Chinese. The account page and the [public profile](#public-profiles) show the longest of each kind among the titles, the losing streak too, for anyone to see; only the notice at the end of a game is the player's alone. When a game ends, the snapshot that ends it carries each account player's streak of three or more (`RoomView.streaks`): a winning streak goes to everyone in the room, screens included, who cheer the player by name; a losing streak goes to its player alone, so that nobody is shown up. The player reads their own streak with a line for the occasion, drawn from a few per tier of length, and whether it is a new record for them. The snapshots of the waiting room and of the next game carry none.

### The account API

`ACCOUNT_API` in `shared/src/accounts.ts`. Answers are JSON, `{ ok: true, ... }` or `{ ok: false, error }`, with a matching status. HTTP because only an HTTP response can set a cookie that scripts never see.

| Address | Does |
|---|---|
| `GET /api/account` | The account, or null |
| `GET /api/account/records` | The record (login) |
| `POST /api/account/replay` | `gameId`; a game to watch again, for an account that took part in it, as a player or as whoever gave its words (login) |
| `POST /api/register` | `username`, `password`; logs in |
| `POST /api/login`, `/api/logout` | |
| `POST /api/account/username` | Renames (login) |
| `POST /api/account/avatar`, `.../avatar/remove` | The image itself, or the default (login) |
| `POST /api/account/password` | Every login ends; this browser gets a new one (login, password) |
| `POST /api/account/email`, `.../email/remove` | Mails a binding link, or unbinds (login, password) |
| `POST /api/email/confirm` | Binds (the link) |
| `POST /api/password/forgot` | Mails a reset link |
| `POST /api/password/reset` | Every browser logged out, this one in (the link) |
| `POST /api/account/delete` | Deletes everything (login, password) |
| `GET /api/profile/<handle>` | A [public profile](#public-profiles), for anyone; `no_such_profile` otherwise |

**Limits** (`server/src/accounts/limits.ts`), counted before any hashing: 5 accounts an hour per address (`ACCOUNTS_PER_HOUR`); wrong passwords 20 a minute per address and 10 in 15 minutes per name (`login_limited`); 60 changing requests a minute per address; a few mails a day per account and destination; 10 avatar changes a day; 100 likes a day.

## Mail

Email is only for resetting a password. An address is bound through a mailed link, and the database keeps only its HMAC-SHA256 with a key derived from `SERVER_SECRET`. Without the secret and the mailer, the API answers `mail_unavailable`. A server started with another secret unbinds every address (`addresses_unbound`). Binding asks for the password; the link works once, for 24 hours. A forgotten password is answered the same for any address; a reset link works once, for 30 minutes, and logs out everywhere. Links carry the secret after `#`, so it never reaches a server or log; the database keeps its SHA-256 (`email_tokens`).

### The mailer

`mailer/` alone holds the mail service's key and writes two fixed mails in both languages (`mailer/src/locales/`). The game server asks over a Unix socket with one line of JSON of five fields, `{"v": 1, "kind", "to", "token", "language"}` (`shared/src/mail.ts`). It builds the link itself; at most 50 mails in 24 hours. It sends through Resend's API; `MAILER_TRANSPORT=print` writes each mail out as JSON instead, for development and tests.

## The agent

`agent/` asks the language model for the AI players' moves ([AI players](#ai-players)), so that the game server needs no network for it, as with the mailer. One line of JSON goes each way over a Unix socket (`AgentRequest` and `AgentReply` in `shared/src/agent.ts`, which each side checks with `AGENT_REQUEST` and `AGENT_REPLY`, refusing a field more or less): a `ping`, or one of a game's requests, each of a kind that no other game's has and naming its game (`shared/src/games/<game>/agent.ts`), with the persona and how long the server waits (`AgentAsked`: `waitMs`, at most 90 seconds, and 3 seconds short of the phase's end). The first game's are a `clue` or a `guess`, with the room's language and settings, the group, the board as the seat sees it and the clues so far. The second game's are a line to `describe` the AI player's word, in a tie too, a `vote` among the numbers it may vote for, a verdict to `judge` a report, and a guess of the students' word once it was voted out (`comeback`), each with the room's language, how long a line may be, the AI player's number and word, none for the PI, the round, every seat as everyone sees it, and the lines, votes and reports so far, as many whole rounds as fit, from the newest back ([games/impostor.md](games/impostor.md#ai-players)). Each game is played with its own code (`agent/src/keywords.ts`, `agent/src/impostor.ts`) and may have a model of its own: the second game's settings are named as the first game's with `AGENT_IMPOSTOR_` in front, and what it leaves unset is the first game's, but that the first game's key goes only to the first game's address (`GAME_MODELS` in `agent/src/config.ts`, [development.md](development.md#environment-variables)). The agent asks the model through OpenAI's chat completions (`AGENT_MODEL_URL`, `AGENT_MODEL`, `AGENT_MODEL_KEY`), for JSON in a schema. It lets the model think at the game's reasoning level (`AGENT_REASONING`, `low` unless set to `off`) for part of a move's wait alone, and asks again without thinking when the time is up or the model fails meanwhile (`agent/src/thinking.ts`): for a clue until 15 seconds before the wait ends, for guesses for 20 seconds at most and until 5 seconds before, and in the second game until 6 seconds before, for the first line of a turn, a vote, a verdict or a guess of the students' word. With less than 5 seconds to think, and for whatever is asked again, the model doesn't think, and a note whose answer came from a question without thinking after the model was let think says so (`fellBack`). Each note says which it was:

- **A clue:** three candidates with the cards each is meant for, the best first, held against the room's rules with `checkClue` and against the board; twice more with the refused ones and why, naming the card that a clue on the board runs into, and else `no_legal_clue`. A clue that aims at more cards than the persona does is refused too. The aim the model is told is the most of the group's cards that its students can work out from the clue, without the other group's cards or Reviewer 2; how the clue is written is a means to it. In a Chinese room, a clue may be a single character, a few that need not make a word, a word or a phrase, or a word with a character or two beside it, and the three candidates are written in three ways, one of them as long as the room allows, up to four characters; after a clue with spaces in it, or one on the board, the model is reminded that a clue has no spaces, or no character of an unrevealed word on the board. In an English room, a clue is one word or, where the room allows, a few. In a Chinese room, the model is also told every character of the unrevealed words on the board, which no clue may contain. Of the clean candidates, a persona that rehearses (`rehearse` in `agent/src/personas.ts`, as Reviewer 1 does) has each guessed by the model as a student of the group, without thinking, up to 3 times each, going round them while the time lasts, until a second before the wait ends, and for as long as no other request waits for the model, and takes the one whose guesses went best on average: a guess that stops by itself or at a neutral card is safe, one that runs into the other group's card worse, and one into Reviewer 2 worst, and among equals the more of the group's cards found the better. Without rehearsals, or with one clean candidate, the first clean one is taken.
- **Guesses:** the cards to reveal, the surest first, at least one and never more than the clue's number, with a sentence of why, which an AI student advising people writes to its group.
- **A line** in the second game: three candidates, held against the room's rules with `checkDescription` (`shared/src/games/impostor/lines.ts`), the check the server runs, which refuses a line that says nothing, is too long, gives the word away or repeats one said before, the first clean one taken; twice more with the refused ones and why, and else `no_legal_move`. The model is told the rules, what everyone at the table knows, its own number and its own word, and never whether its word is the students': a Reviewer 2 isn't told that it is one, and the PI is told that it has none, and to work out the students' word from the others' lines and blend in. A player with a word is told that it may be a Reviewer 2 without knowing it, and writes first, as the first fields of its answer, which the model writes in order, a judgment that its line goes by: `closest`, the other word closest to its own, a specific word, never a category, and, after the first round and for a line that breaks a tie, `fit`, which of the two the others' lines fit, its own, the closest, or unclear, the closest only when they clearly fit it better. In the first round, with little to go by, a line says only the field or the kind that both words belong to, or a property both have, never a use, a mechanism or a feature that tells them apart; after that, when the lines fit the closest word, it describes that word, vaguely, as those who have it would, never what only its own word has, as a player with the odd word plays; when that is unclear, only what both words have; and when they fit its own, a line that those who share it recognize and the others can't work out. The judgment goes into its note (`judgment`), for the AI log, never into the game.
- **A vote, a verdict and a guess of the students' word,** the first two with a sentence of why, all in the room's language: a number that isn't one it may vote for is an abstention, a verdict that isn't one of the game's is an abstention too, and a guess of its own word is none. A player with a word is told the points of a vote and of a win, as `score.ts` sets them, writes first the closest word and which of the two the lines fit, as for a line, and votes by that: when they fit its own, for the player whose lines fit it least; when they fit the closest, never for a player whose lines fit it, nor, while a game has two Reviewer 2s in it, for one whose lines fit its own word better than the closest, but for one whose lines fit neither, named as the PI while one may still be in, or it abstains; when that is unclear, for the player whose lines fit the others' least, or it abstains. Judging a report, it writes no judgment, and is told only that it may be a Reviewer 2 without knowing it.

At most `AGENT_CONCURRENCY` requests go to the model at once and `AGENT_QUEUE` wait their turn; past them, `busy` at once, and a request whose turn hasn't come when its wait is over is `busy` then, while the server still listens. Thinking holds the model for long, so the requests with it are hurried for those waiting: each waiting request is promised 3 seconds of the model before its wait ends, the requests with the model are told to stop thinking in time for that, and are asked again without, a PI among them giving its clue without further rehearsals, and one that gets its turn when the waiting ones can't wait for thinking goes without from the start (`hurryAt()` in `agent/src/agent.ts`); a waiting request that would be late even if those with the model stopped at once, as one asked again late in a phase may be, hurries nobody, since it is `busy` whatever they do. So the AI players of one room think as long as they may, and when many move at once, as the AI players of the second game vote, or the AI players of several rooms, the first ones think less and the last ones not at all, and every move is in time, but for the rare one whose answer without thinking the rules refuse, which is asked again; an operator whose model answers several requests at once raises `AGENT_CONCURRENCY`. A model that answers nothing usable, or nothing in time, costs that request alone (`no_answer`); a service that can't be reached or refuses is `model_failed`, which takes the AI players offline. A ping asks the service of every model that plays a game whether it lists the model, without loading one, and answers with them all only when each is there. With a key, the service's address is HTTPS, unless it is on the same machine, so that the key never goes over the network in the clear. Each game's prompts are versioned (`PROMPT_VERSION`: `keywords-6` in `agent/src/prompts.ts`, `impostor-2` in `agent/src/impostorPrompts.ts`), and every answer notes the model and the version. The agent's log says what kind of request came, how long its answer took and whether it was one, never the board or the answer.

## Avatars

The page crops the picture and encodes it at 256 by 256 as WebP or JPEG, within 30 KB. **The server never decodes an image:** it reads the header only (type, size, still, at most 64 KB; `server/src/accounts/avatars.ts`). Files live in `avatars/` under `DATA_DIR`, named by SHA-256. Served under `/avatars/<name>` with `nosniff`, `default-src 'none'` and a year of `immutable` caching. The operator's `admin.cjs avatar remove <username> [--ban]` takes one down ([development.md](development.md#accounts-and-email)).

## Threat model

- **Guessed passwords:** slow salted scrypt and limits per address and name before hashing.
- **Who has an account:** answers that reveal a taken name are limited, `login_failed` is the same for a wrong name or password, and the friends messages answer a name that is no account's as they answer a stranger's, except the request, which costs one of the day's 30, and the search, which says whether a whole username is an account's, for one of the account's 30 an hour, counted before the name is looked up. It takes nothing but a whole name, so that nobody lists accounts by a part of a name or counts through them by number; a link to a page leads to the page, which its holder could open anyway.
- **Stolen logins and other sites:** a random secret, kept hashed, only in a hardened cookie, HTTPS only; `Origin` and `Sec-Fetch-Site` checks, no CORS, no framing; password change, binding and deletion ask for the password.
- **Links and mail:** 256 random bits after `#`, kept as hashes, short-lived, used once; two fixed mails from a mailer that alone holds the key.
- **Who plays with whom:** what two friends have played together, and the titles it earns, go to the two of them alone, each on their own friends list and on the other's profile; nobody else in a room or at a profile is sent them, and nothing of them is stored, since they are worked out from the records and the friendships when asked.
- **The agent and the model:** the agent is asked with no more than a seat may see, so an AI student never learns the key, and with no chat; its answers pass a strict schema and then the rules, as a player's messages do, so a model that answers nonsense, or a word of the chair's written to steer it, makes at most a bad clue, a wrong card, or a sentence of at most 200 characters in its own group's chat, where the AI student says why it chose a card. In the second game, an AI player is told no more of the others than everyone at the table knows, and its own word, so a model that answers nonsense, or a setter's word or a player's line written to steer it, makes at most a bad line, as long as the room allows, a wasted vote or verdict, or a wrong guess of the students' word; the reasons it gives go to the AI's log alone.
- **A leaked database** holds usernames, password hashes, hashes of random secrets, keyed HMACs of email addresses, records with their points and titles, who is friends with whom and who asked whom, the lines of the requests not answered yet and the names that friends give each other, the links and the lines that accounts wrote on their profiles and who likes whose, the records of every game, with their boards, the clues and the groups, or the roles, the words and their setters, and their logs, with every move, every line of the groups' chats and of the second game's descriptions and off-field chat, when it came and the player ID that made it, and which player ID in a game was which account, how each player rated the game and whom they guessed to be its AI players, by player ID, the words adopted from the games and the accounts that gave them, which accounts may have AI players and the AI's logs, with the models' clues and reasons, the feedback, with the contacts of the last 90 days, the user agents of bug reports and the games it was sent about, and the reports, with who reported whom, the name the player had, in which room and the note; no IP addresses.

## Logging

One JSON object per line on stdout, never a token: rooms created and closed (`empty`, `idle`, `stale`, `chair`, `flood`, `restart`), games started and ended, errors, the `stats` line, the limits' line of the minute (`limited`), and named events such as `listening`, `startup_failed`, `database_opened`, `database_migrated`, `records_recounted`, `snapshot_failed`, `storage_full`, `feedback_received`, `feedback_purged`, `report_received`, `account_created`, `mail_not_sent`, `words_clashed`, `match_ended`, `agent_added`, `agent_failed`, `agent_move_refused`, `agent_down`, `agent_up`, `thanks_list_read`, `thanks_list_skipped`, `busy_started` and `busy_ended`; Node's warnings come as `warning` lines, so every line is JSON. The two lines that may mean trouble, `limited` and `busy_started`, have `level: "warn"`, so that whatever watches the log can raise an alert on them.

## Status

`server/src/stats.ts` counts for the `stats` log line and `/status.json`: no addresses, tokens, names, ids or room codes. The `stats` line, every 5 minutes: rooms, members, connections by transport and country, memory, and on a server with an agent, the AI players in rooms, whether the agent answers and their steps of the last hour, which `/status.json` gives too. Neither the log nor the statistics say who is connected or in which room, by name or by id: only `/live.json` on the local status port does, by account id, at the moment it is asked.

With `STATUS_PORT`, the server gives the operator data on a port of its own, as JSON alone, with no page: what only the running process knows, and as little of it as will do. The operator's own tools read it and show it as they like; the repository has none. The port listens on `127.0.0.1` only, which is why it needs no password, and answers only a `Host` of `localhost`, `127.0.0.1` or `[::1]`, with any port or none, as a client on the same machine sends it, whatever local port it reaches the server through; anything else gets a bare 421, so that a page elsewhere can't read it through a browser on the machine by pointing a name of its own at the address (DNS rebinding). It answers GET and HEAD alone, with `Cache-Control: no-store`, and any other path with 404 (`server/src/status.ts`):

- **`/status.json`**, the numbers above, with no name or id, and whether the server is busy (`busy`; [Limits and housekeeping](#limits-and-housekeeping)).
- **`/live.json`**, who is connected and who is in each room at that moment (`server/src/live.ts`): each connection, with the id of the account it is logged in to, or `null` for a guest, the code of the room it is in, as a member or a screen, or `null`, its country and its latency; and each room, by its code, with its members, each by account id, by guest number or, for an AI player, by persona alone, whether they are online, since when they have been offline, in ISO 8601, and whether an AI plays for them, and how many screens show the room. It gives no username or other name, address, user agent, token, chat, board, word, hidden role or room setting: the operator looks a username up themselves, and the log has the rooms' settings already. It is worked out for each request, and never logged or kept.

The feedback and the reports are in the database, and the operator reads them with `admin.cjs feedback list` and `admin.cjs reports list` ([development.md](development.md#accounts-and-email)). Countries come from Cloudflare's `CF-IPCountry` header, read only with `TRUST_PROXY` on; any other proxy must drop it ([development.md](development.md#running-in-production)).
