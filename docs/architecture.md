# Architecture

How the app is put together. The hard constraints behind it are in [rules/constraints.md](rules/constraints.md), and the rules of the first game are in [games/keywords.md](games/keywords.md).

## One process, one port

A single Node process serves everything on one port: the built front end, `/healthz`, the account API under `/api/`, the avatars under `/avatars/`, and Socket.IO under `/socket.io/`. Rooms live in the server's memory and end when the process restarts. What the server keeps on disk is the feedback that players send and the accounts, in a SQLite database, and the avatars, as files beside it; see [Data](#data). The status page for the operator is the one exception to the one port: when it is on, the same process serves it on a second port that only its own machine can reach; see [Status](#status).

The game server can't reach the internet, so a second program, the mailer, sends the mails of accounts. It serves nothing to players: the game server asks it over a Unix socket on the same machine; see [Mail](#mail).

| Layer | Where | What it does |
|---|---|---|
| Shared | `shared/src/` | Types and the rules that both sides run, such as the checks of a nickname and of a clue. `schemas.ts` holds the message schemas, for the server alone |
| Server core | `server/src/core/` | Rooms, players, connections, the chair's controls, limits, the word library |
| Server games | `server/src/games/<game>/` | One module per game: its seats, its rules and what each player sees |
| Server accounts | `server/src/accounts/` | Passwords, logins and their cookie, the account API over HTTP, email fingerprints, the way to the mailer, and avatars |
| Server store | `server/src/store/` | The database, its migrations and snapshots, and the feedback and accounts kept in it |
| Mailer | `mailer/` | The program that sends the mails of accounts, which only it can; see [Mail](#mail) |
| Client core | `client/src/core/` | Connection, rooms, lobby, language, storage |
| Client games | `client/src/games/<game>/` | Each game's screens |

Adding a game means adding a module on each side, without changing the core.

## Rooms

- **Codes.** A room has a 4-character code in Crockford's base32 (digits and capital letters without I, L, O and U), which gives about a million codes. Links look like `/room/K7QX`, and the interface shows the code as a manuscript number, `R2-K7QX`. A typed code is read in any case, with or without the `R2` prefix, with spaces or dashes anywhere in it, and with I and L for 1 and O for 0. `parseCode()` in `shared/src/codes.ts` does the reading for both sides, so the client never refuses a code that the server would take.
- **Room IDs.** Each room also has a random `roomId`. Codes are reused after a room closes, so every snapshot carries the `roomId`, and a client that has been in a room gives it whenever it asks to be let back in: in the handshake, in `room:join` and in `room:watch`. When the code has gone to another room since, the server answers that the room is gone, and nobody ends up in a stranger's room.
- **Language.** A room's language is set when it is created and never changes. It decides both the interface language inside the room and the words on the cards.
- **Phases.** A room moves from `lobby` to `playing` to `ended`, and back to `lobby` for another game.
- **Games.** The room gives each game a random `gameId`, which its view shows while the game is being played and after it has ended, and counts the games it has started in `round`. The chair's messages about a game say which game they mean.
- **Matches.** A room is created as an ordinary room or as a match, which plays a set number of games and ranks the players by their scores; see [Matches](#matches).
- **The chair.** The first member chairs the room. Only the chair can change the fields or the game's settings, start, withdraw or replay a game, shuffle the groups, end a match early and start another or go back to an ordinary room, move someone to the spectators, remove someone, hand the chair over, or close the room for everyone. The chair can be handed only to a member who is online. When the chair leaves, or has been offline for 3 minutes while someone else is online, the chair passes to the member who joined first among those online.
- **Playing or watching.** A newcomer says in `room:create` or `room:join` whether they have come to play, with `play: true`, or only to watch. The game decides what playing means: the team word guessing game gives a player a student's seat ([games/keywords.md](games/keywords.md#seats)). A newcomer who doesn't say watches. A member who comes back keeps the seat they had, whatever they say.
- **Removal.** A member the chair removes can't come back from the same browser for 2 minutes, and for those 2 minutes nobody else can take the name they had. A player is known only by the token in their browser, so this doesn't keep out someone who opens another browser and picks another name: it gives the room a pause, and the chair can remove them again.
- **Revisions.** Every change bumps the room's `rev`. A message that is granted but changes nothing, such as asking for the seat one is in, bumps nothing, and nobody is sent a snapshot for it.

## Players and identity

- **Tokens.** The first time a browser connects, the server gives it a random 32-byte token, which the browser keeps in local storage. The server accepts any well-formed token it is given, so identities survive a server restart. It issues a new token only when the browser has none.
- **The session.** The first thing the server sends on every connection is `session`, with its `version`, the `account` that the connection is logged in to, with its username and avatar, or null, and, when it has just issued one, the `token`. A page that was loaded from an older version of the server learns from it that it should reload. The server sends `session` again when the account is renamed or changes its avatar.
- **Member keys.** The server never stores tokens. It works with the token's SHA-256 hash, the member key, which never leaves the server. The key is kept with each connection, in each room's list of members, for 2 minutes in a room's list of those the chair removed, and by a game module for whatever it has to remember about a player who leaves and comes back, such as which group they played for. A token itself is only held by Socket.IO, in the handshake of its connection for as long as the connection lasts.
- **Player IDs.** Players know each other by a separate random player ID. So no token ever leaves the browser that holds it, and nothing anyone else sees can be used to impersonate a player.
- **Tabs.** Two tabs with the same token are the same player. Both can act, and the player is online while either is connected.
- **Accounts.** A browser that is logged in to an account is that account instead, on every device: its member key is the SHA-256 of the account's ID, which, like any member key, never leaves the server. So two phones logged in to one account are one player, as two tabs are, and the chair's removal holds for the account on any browser. See [Accounts](#accounts).
- **Nicknames.** A nickname has 1 to 16 characters, with full-width forms folded and spaces collapsed. An emoji counts as one character, however many code points it is built from, and the message schema lets through every name that these rules would take. Whatever a reader can't see is refused: control and format characters, the characters that Unicode says to ignore (zero-width spaces, soft hyphens, the Hangul fillers and the like), private-use characters, a name that shows nothing at all, a mark at the start or after the last letter, and more than four marks of a kind on one character. The silent characters that emoji and the letters of some scripts are built with stay: the joiners, as Sinhala and Persian need them, the variation selectors and the direction marks. Names must be unique within a room, ignoring case and those silent characters. The rules are in `shared/src/names.ts` and `shared/src/text.ts`, which the group chat shares, so that the client can apply the very same ones. A guest can't take a registered username as a nickname, compared as usernames are, which also folds full-width forms: the server answers `name_reserved`. A player with an account is called by the username in every room.
- **Storage.** The client reads and writes local storage only through `client/src/core/storage.ts`, which never throws. When storage is unavailable, values live in memory, and the game still works: the player just can't get back to their seat after a refresh.

## Messages

Everything after the page load goes over Socket.IO, but for the account API, which is HTTP; see [Accounts](#accounts). `shared/src/protocol.ts` describes the room messages, and each game defines its own, named `<game>:<action>`.

- **Answers.** Every message from the client gets an acknowledgement: `{ ok: true, ... }` or `{ ok: false, error }`. That includes a message the server doesn't know and one with more in it than a payload, which are `bad_request`. Error codes are shared, and the client shows each one with the text under `errors.<code>` in the locale files. The server never sends interface text, only the words on the cards.
- **In order.** The messages of one connection are handled in the order in which they arrived, room messages and game messages alike, so a game action that is sent right after the start of its game finds the game started.
- **Validation.** The server checks every payload against a zod schema before it looks at it. The schemas are in `shared/src/schemas.ts`, which the server imports as `@reviewer2/shared/schemas`. The client never imports that module, and ESLint refuses it if it tries: zod would add half again to the page's script, and it probes `new Function`, which the Content Security Policy below refuses.
- **Snapshots.** After every change that anyone in the room can see, the server sends each connection in it its own complete snapshot, `room:state`. A second tab of a player who is online changes nothing for the others, so only that tab is sent one. The client keeps the snapshot with the highest `rev` for its `roomId`. The server sends the snapshots before it answers the message that caused them, so an answer never arrives before the state it refers to.
- **Quick reactions.** Any member, spectators included, may send one of three reactions with `room:emote` (`EMOTES` in `shared/src/protocol.ts`), one every 10 seconds. The wait goes by the member key, so another tab, or leaving and coming back, doesn't cut it short, and a reaction sent too soon is refused with `emote_cooldown` and `waitMs`, how much of the wait is left, so that the tab it came from counts down the right time. The server passes it on at once to every connection in the room, the sender's own and the screens' included, as `room:emote` with the room's ID, the sender's player ID and the reaction. A reaction is a moment rather than a change to the room: it bumps no `rev`, no snapshot carries it, and whoever is offline misses it. The client knows the sender's name from its snapshot, and the text and the sound of each reaction are its own.
- **No interleaving.** Handlers never await anything between reading a room and writing it, so two messages can't interleave.
- **Closing.** `room:closed` tells a connection that its room is gone for it. The reason is `removed`, `expired`, `left` (from another tab), `closed` (the chair closed the room for everyone) or `restart`. It goes to the connections that are open at that moment. Whoever is offline when the chair removes them, when the sweep drops them or when the room closes has no connection to tell, and finds out when they come back: from the handshake, which answers the room's old ID with `expired`, or from the answer to `room:join`. The connection that sent `room:leave` or `room:close` is answered instead of told, since its page knows what it asked for, and that member's other connections hear `left`, whichever of the two it was.

## The handshake and reconnecting

Phones drop their connection whenever the screen locks or the browser goes to the background, so reconnecting is routine:

- **Sooner detection.** The server pings every 10 seconds and gives up after 8 more, sooner than Socket.IO's defaults, so dead connections are noticed quickly.
- **The handshake.** The client sends `{ token, code, roomId }`. A connection whose token belongs to a member of that room is put back into it before any of its messages run, so a message that waited out the disconnect lands in the right room. A screen sends `{ watch: code, roomId }` instead and is put back to watching. The server checks the handshake against a schema like any payload, and takes a field that isn't what it should be for a missing one.
- **The handshake only brings back.** It lets nobody into a room for the first time: a token that isn't a member's, or a screen that gives no `roomId`, gets no answer from it. Its one answer is `room:closed` with the reason `expired`, to a `roomId` that is no longer the code's. So a client always follows the handshake with `room:join` or `room:watch`, which are answered: that is where a newcomer is asked for a name, and where a player learns that the room is full, that they were removed or that the code belongs to no room.
- **Stale actions.** Every game action carries the game and turn it was meant for, and the chair's start, withdrawal and "play again" say which game they mean. A late or repeated one is refused as `stale` instead of landing in a later turn or in another game: a second tab whose connection had stalled can't start a game that nobody asked for, or clear away the result of the next one.
- **On the client** (with the lobby UI): it checks the connection with `sys:ping` when the page becomes visible again, when the browser restores it from its cache, and when the network comes back, and reconnects at once if the ping goes unanswered, or if its request to enter the room is. It drops anything that was queued while offline, and sends nothing while disconnected. It stops trying to rejoin a room that no longer exists, and shows only the room it is on, not the snapshots that still come for a room it has left.

## Games

A game is a module that implements `GameModule` (`server/src/core/game.ts`). The core owns the room, its members and the chair; the module owns its data and decides:

- the seats, where a newcomer who has come to play sits, and what the chair's bench and shuffle do to them;
- its own settings: their defaults for a room's language, and whether it takes the settings that the chair sends with `room:create` and `room:settings`. The core passes them on as they came and knows nothing of what is in them;
- whether a game can start, and, in its view, what still keeps it from starting;
- how a game starts, how many words it needs and what happens on each of its messages;
- what happens by itself when its time comes, such as the end of a turn whose time has run out (see below);
- what each viewer sees;
- and, for a game that can be played as a match, how a match groups its players and scores them ([Matches](#matches)).

A module's data is immutable: every call returns new data. `views()` is the only way a game's data leaves the server. The room asks it once for a snapshot and calls what it returns for each member and for the screens, so a game builds what everyone sees once, and shows each player only what that player may know. `server/test/fakeGame.ts` is a minimal module that the core's tests use.

The room draws the words for each game from the fields that the chair chose, preferring words it hasn't played with yet, and hands them to the module. After every change to a module's data during a game, the room asks the module whether the game is over.

A module may also say which two words must not be in the same game, with `wordsClash()`; the team word guessing game keeps apart two words of which one gives the other away ([games/keywords.md](games/keywords.md#setting-up)). The room then draws no two words that clash (`drawWords()` in `server/src/core/words.ts`):

- It takes the words of the fields in a random order, those it hasn't played with yet first, and keeps each word that clashes with none of those it has kept, until it has enough. That is one pass over the words, so it always ends, and it is quick: it only compares a word with the few kept before it.
- A word that clashes with none is always kept, so the pass fills a game whenever the fields have as many such words as a game needs; in every list of the library, at least two thirds of the words clash with none. A word that clashes with at most d others keeps at most d of them out, so the pass also fills a game whenever the fields have at least d + 1 times as many words as a game needs; all the lists together have 3,088 words, of which none clashes with more than 35 others, so they do, while a single list of about 300 words doesn't meet this bound. `scripts/check-words.mjs` also makes sure that each list on its own has a board's worth of words of which no two clash ([../words/README.md](../words/README.md#contributing)).
- Should the pass still come out short, which takes a small pool with many clashes, the room draws again one word at a time from the first 500 words of the same order, each time the word that clashes with the fewest of those drawn, then the one that clashes with the fewest of the words still open (those that clash with none drawn), and then the one that comes first. This compares every two of those 500 words once, which takes a small fraction of a second, and it ends after as many steps as the game needs words. It often finds a game without clashes where the pass found none.
- When the clashes leave out some of the unused words, the draw takes used words in their place, at random, but those of the last game only when no other is left, and the room keeps its memory of the words it has played: the words left out are still unused, and come first next time. The room starts over, remembering only the words of the game just drawn, once every word of its fields has been played. When some words clash all the same, the game starts anyway, and the server logs `words_clashed` with the room's code, language and fields and the number of pairs that clash.

A module that keeps time says when it next has something to do, with `deadline()`, on the room's clock, which `GameContext.now()` reads. After every change to a room, the server sets a timer for that moment, at most one for each room, and when it fires, the room calls the module's `tick()` and sends everyone the new state. The room also calls `tick()` before each of the game's messages, so that a message which arrives after a deadline finds what the deadline brought, however late the timer is: an action meant for a turn whose time has run out is `stale`, even before the timer has fired. A refused message can therefore still bring a new snapshot. A deadline that the data no longer has, because the game ended or went back to the waiting room, takes its timer with it, and so does a room that closes. What `tick()` changes bumps the room's `rev` but doesn't count as activity for the sweep.

A module that throws can't take the server down or leave a room half changed. The room asks the module first and changes itself afterwards, so the room stays as it was; the message is answered with `internal`, and the error is logged. Where no message is waiting for an answer, in the handshake, on a disconnect, at a deadline and in the sweep, the error is logged and the rest goes on. A view that can't be built costs only that viewer's snapshot.

## Matches

A match is a room that plays a set number of games in a row, scores every player in each of them, and ranks the players by their totals at the end. The chair makes a room a match when creating it, with its rules (`MatchRules` in `shared/src/match.ts`), which the schema checks in full:

- **Games:** 1 to 10, 3 unless the chair says otherwise.
- **Groups:** `fixed`, the same for the whole match, or `switch`, made again after every game.
- **How they are made:** `random`, drawn by the server as the game starts, or `choose`, chosen by the players in the waiting room. With fixed groups, this is how the first game's groups are made.

The room keeps the match (`server/src/core/match.ts`); the game decides how its players are grouped from one game to the next and how each of them scores, through `GameModule.match` (`server/src/core/game.ts`). A game without it can't be played as a match. The team word guessing game's part is in [games/keywords.md](games/keywords.md#matches).

- **Scores** are counted on the server alone, when a game ends by itself, and once for each game. A game that the chair withdrew counts for nothing, and isn't one of the match's games: the match goes on. Everyone sees the same table, `RoomView.match`: which game it is, each player's total, their place, and their points in the game being played, as they stand, in the game that has just ended, or, in the waiting room, in the last one scored.
- **Players are known by their member key,** so whoever reloads the page or comes back after a dropped connection finds their total where they left it. A guest who logs in during a match and comes back to the room takes their line to the account, as they take their seat ([Accounts](#accounts)); when the account has a line of its own already, from before it left the room, the two are added up, and once the match is over, the account keeps the place and the total that the guest was ranked with. Logging out makes the browser someone new.
- **Who is listed:** everyone in a seat when a game starts, with no points if they are new, and anyone who scores. A player who leaves the room stays in the table, marked as having left, and is ranked again on coming back. A newcomer who comes to play while a game is on watches it, and plays from the next one.
- **The settings,** the word lists included, stay as they are once a game of the match has been scored, until the match has ended.
- **The end.** Once the last game has been scored, the players who took part in a scored game and are still in the room, online or not, are ranked by total, with ties sharing a place (1, 1, 3). Everyone with the highest total is awarded the Best Paper Award, and, with three or more ranked players, everyone with the lowest is the game's black hole; when all have the same total, nobody is awarded anything. The places stay as they were then, whoever leaves afterwards. The chair may end a match early, which withdraws a game in progress: the players are ranked as they stand, but nobody is awarded a title and no account keeps the match.
- **Afterwards,** the chair starts another match, with the same rules or others, or makes the room an ordinary one again.

Each ranked player with an account keeps the match on their record, with their place, the number of ranked players, their total and their title, and is awarded the title through `TitleStore.award()` (`server/src/store/records.ts`), in one transaction. The database keeps a match once for each account and a title once for each match, however often the end is reported. A guest plays, scores and is ranked the same, and nothing is kept.

## Screens

A screen, such as a projector in a lab meeting, watches a room without a token and without a seat. It starts with `room:watch`, and comes back after a dropped connection through the handshake, by the `roomId` it was sent. The server gives it the view that a spectator would get, so even a chair who is also a captain can put the board on the wall without showing the key. A room can have up to 5 screens.

A screen has no name, so all that anyone sees of the screens is how many there are, in the room's view. Whoever has the code can put one up, which could fill all five places or let someone watch who should not. So the chair can send every screen away at once with `room:dismiss`: they get `room:closed` with the reason `removed`, and the ones that belong there are put up again. A player whom the chair has just removed can't watch from the same browser for the same 2 minutes: a screen that the browser had up goes with the seat, and it can't put up a new one.

## Limits and housekeeping

- **Message rate.** Each connection may send about 10 messages a second, in bursts of up to 20.
- **Per address.** Each address may try to create 5 rooms a minute, or as many as `ROOMS_PER_MINUTE` allows ([development.md](development.md)), counting the attempts whose fields turned out not to do, because checking them means going through their words. It may send 20 codes a minute that belong to no room, which keeps anyone from trying codes until one fits. Past that, the address is refused whether or not its next code is right. Joining and watching count alike, and the handshake gives a bare code no answer at all, so there is no way around the count. It may also send 3 pieces of feedback every 10 minutes, or as many as `FEEDBACK_PER_10_MINUTES` allows; see [Feedback](#feedback).
- **In one place.** `SocketLimits` in `server/src/core/socket.ts` holds all of these numbers, with their defaults, as `RoomLimits` in `server/src/core/rooms.ts` holds those of the rooms.
- **Never for those who have been there.** An address is rarely one person: a lab shares one. So the limit never holds up someone who is in the room already, by their token or on the same connection, or who gives its `roomId`. A wrong `roomId` finds nothing whatever the code, so it can't be used to try codes. A member always gets back in; only newcomers at that address wait out the minute.
- **Behind a reverse proxy,** every connection comes from the proxy, so set `TRUST_PROXY` to take the address from `X-Forwarded-For` instead; [development.md](development.md) has the settings. Otherwise all players share the limits of one address. IPv6 addresses count per /64 network.
- **The clock.** Every limit and every wait here is a length of time, and so are the games' deadlines, so the server measures them all with a clock that only runs forward and that a correction of the system's clock doesn't move. Its readings never leave the server: a game's view says how long is left, not when.
- **Sizes.** A message may be up to 16 KB. A room holds up to 30 players and 5 screens, and the server up to 2000 rooms.
- **The sweep.** Once a minute, the server closes rooms in which nobody has been online for 30 minutes, and rooms in which nothing has happened for 6 hours. It also drops members who have been offline for 10 minutes from waiting rooms, closes a waiting room that this leaves empty, and passes on the chair of anyone who has been away for 3 minutes. Those 10 minutes count only time in the waiting room: a player whose phone was locked during a game still has their seat when the room goes back to the waiting room, and 10 minutes from then to return to it.
- **Restarts.** When the process is asked to stop, it first tells every connection `room:closed` with the reason `restart`. It then ends each connection in the way that sends what is still waiting to go out, and gives that up to 2 seconds before it closes, so that the notice also reaches a connection on a long poll or a slow network. A room that someone made during those seconds is told the same before the server goes. Last, it waits for a snapshot that is being written and closes the database. When all of that takes more than 5 seconds, the process ends regardless, with the exit code 1 and the log line `stop_timed_out`; WAL keeps the database whole for the next start.
- **Starting.** A setting that is wrong, a word library without a list or a term that can be read, or a database that can't be used stops the server before it opens its port, with `startup_failed` in the log and the exit code 1. So does a port that something else has, with `listen_failed`.

## HTTP

- **Caching.** Files under `/assets/` have a content hash in their name and are cached for good. Everything else, `index.html` included, is sent with `no-cache`, so that a browser never keeps an old page that asks for assets the new build no longer has. A missing asset is a 404 rather than the page.
- **Bundles.** The front end is one bundle without lazily loaded chunks, for the same reason.
- **Security headers.** Every response carries a Content Security Policy (`script-src 'self'`, no framing, and the `ws://` and `wss://` origins spelled out for older iOS browsers), `nosniff` and a referrer policy.
- **Read-only, but for the account API.** Every path answers GET and HEAD alone, with 405 for anything else, except the account API under `/api/`, whose requests that change something are POSTs; see [Accounts](#accounts). An avatar under `/avatars/` has headers of its own; see [Avatars](#avatars).

## Data

The server keeps two things on disk: the feedback that players send, and the accounts ([Accounts](#accounts)), in one SQLite database, with the avatars as files beside it ([Avatars](#avatars)).

- **The data directory.** `DATA_DIR` names it ([development.md](development.md)). The database is `reviewer2.db` in it, with the `reviewer2.db-wal` and `reviewer2.db-shm` files that SQLite keeps beside it while it is open, and its snapshots are in `snapshots/`. The directory must be there: when it isn't, the server refuses to start, rather than start an empty database somewhere that nobody looks. The server makes `snapshots/` and `avatars/` itself, and never changes the permissions or the owner of anything. In production, systemd's `StateDirectory` gives the service a directory of its own, and the service's umask keeps what it writes private.
- **Without `DATA_DIR`,** the database is in memory. It has the same schema and goes through the same code, but nothing is written to disk, it is lost when the server stops, and it has no snapshots. The `database_opened` log line says which of the two the server has.
- **SQLite,** through Node's built-in `node:sqlite`, with no npm package. It is synchronous, so, as with a room, nothing can come between a read and the write that follows it. The database runs in WAL mode, so that reading never waits for writing and a snapshot can be taken while the server writes. A write that finds the database locked waits up to 5 seconds rather than fail. Secure delete is on, so that what is cleared, such as a contact, is overwritten in the file instead of lingering in its free pages.
- **Migrations.** `PRAGMA user_version` holds the version of the schema, and `server/src/store/migrations.ts` lists the migrations in order. On start, the server runs the ones that a database hasn't had, all in one transaction with the new version number, so that a database is at the version it was at or at the latest, never in between. Foreign keys are off while they run, as SQLite asks of a migration that rebuilds a table, and a migration that leaves a row pointing at nothing is rolled back. Before it migrates a database that has data in it, it takes a snapshot, `reviewer2-<time>-before-v<version>.db`, which is kept for a week. A start whose migration fails takes one too, and the service is started again every few seconds after such a start, so of the snapshots to one version only the latest is kept. A database at a newer version than the server knows, as after going back to an older release, stops the server: run the newer one, or restore the snapshot from before the upgrade.
- **Snapshots.** Every hour, and on start unless the latest is less than an hour old, `backup()` copies the database into a temporary file a few pages at a time, while the server goes on as usual. The start counts because a server that is restarted more often than once an hour, as on a day of many releases, would otherwise never take one. The copy is turned from WAL into an ordinary rollback journal, so that it is one file that can be copied into place as it is, and then gets its name, such as `reviewer2-20261009T130000Z.db`, with the time in UTC. The last three are kept. A snapshot that fails is logged as `snapshot_failed`, and the next hour tries again; old snapshots that can't be deleted are logged as `snapshots_not_pruned`. To restore one, stop the server, copy the snapshot over `reviewer2.db`, delete `reviewer2.db-wal` and `reviewer2.db-shm` if they are there, and start it again. The snapshots are on the same disk as the database; copies elsewhere are for the machine to make.
- **The disk.** The server takes no more feedback once it has 10,000, or once the feedback holds more than 50 MB, counting the bytes of its text, contact, user agent and version. Past 1 GB for the whole database, it keeps nothing new at all: no feedback, no new accounts and no records of games or matches, and logs `storage_full` once; the accounts there go on working. The avatars may take 2 GB together. So nobody can fill the disk, and the directory needs room for the database, its WAL, the snapshots and the avatars: about 7 GB at most.
- **What goes with an account.** Everything of an account, its logins, the links in its mails, its record of games and matches and its titles, is deleted with it, through the foreign keys, and secure delete overwrites it in the file; the server then truncates the WAL as it does for contacts. Snapshots taken before still hold it for as long as they are kept, and copies elsewhere for as long as their own retention says.
- **Making room.** The server never deletes feedback; the operator does, when the limit is reached or to be rid of spam. Stop the service, open the database with `sqlite3 /var/lib/reviewer2/reviewer2.db`, delete the rows (`DELETE FROM feedback WHERE id IN (...)`, or by `created_at`), run `VACUUM`, and start the service again. `VACUUM` matters: the limit is the size of the file, which deleting alone doesn't shrink, and it also leaves what was deleted in the file's free pages, which `VACUUM` drops. An id is never given out again, so a number in the log still names the feedback it named. The snapshots that were taken before still hold the deleted rows, for as long as they are kept. Doing this while the server runs works too, but a read or write that is left open in sqlite3 makes the server wait up to 5 seconds for each of its own writes, and keeps it from truncating its WAL.

## Feedback

Players can send the author feedback from the foot of the home page and of a room: a suggestion, a bug or something about the word lists. The status page shows it to the operator ([Status](#status)).

- **The panel.** "Send feedback" opens a panel, where the player chooses what the feedback is about, writes 1 to 1000 characters, and may leave a contact of up to 100 characters, such as an email address or a WeChat ID. The panel says that only the author can read it, and that the contact is used only to reply. The rules in `shared/src/feedback.ts` clean the text as the chat is cleaned, line by line, so that it keeps its line breaks; the client runs them while the player types and sends the text as they clean it, which keeps the message well under 16 KB, and the server runs them again before it keeps the text.
- **What is kept:** the text, the contact, the kind, the build of the page that sent it, the language the page was shown in, whether it came from the home page or from a room, and the time it arrived, on the server's clock. With a bug, and only then, the browser's user agent comes along too, which the server reads from the connection, and the panel says what it holds: the names and versions of the browser and the system, and on some phones the model.
- **What isn't:** nothing that says who sent it. No address, nickname, token or member key is kept, and nor is the room's code or ID: the page is only "a room". A field that the message has besides those above is dropped.
- **The limits.** One address may send 3 pieces of feedback every 10 minutes, or as many as `FEEDBACK_PER_10_MINUTES` allows ([development.md](development.md)), counted in memory. Only what was kept counts, so that a player who is told to shorten the text doesn't lose a turn for it. The same feedback from the same address, with the same kind, text and contact, is kept once in those 10 minutes: when the answer to the first is lost on a slow connection, the panel asks the player to try again, and the second try is answered as the first was, without a second copy. Once the server takes no more ([Data](#data)), players are told so, and the log says so once, with `feedback_full`, until feedback is taken again.
- **Contacts are cleared after 90 days.** On start and every hour, before the hourly snapshot, the server clears every contact that came more than 90 days ago, on the system's clock, and logs how many with `contacts_cleared`. The feedback itself stays. Secure delete overwrites a cleared contact in the database file, and a checkpoint right after it writes the WAL back into the file and truncates it, so that the WAL doesn't keep the pages as they were either. The checkpoint can't be done while another connection, such as the operator's sqlite3, is in the middle of the database; the server doesn't wait for it, `contacts_cleared` then says `walTruncated: false`, and every hour after that tries again, with a `wal_truncated` line that says whether it was, until it is done. An account that is deleted is dropped from the WAL the same way. A snapshot that was taken before the contact was cleared still has it, for as long as the snapshot is kept: a few hours for an hourly one, and a week for one from before a migration, which may also hold contacts that ran out while the server was stopped.
- **The log** gets one line for each piece of feedback, `feedback_received`, with its number and its kind, and never its text or contact: `journalctl -u reviewer2 -g feedback` lists them.

## Accounts

Accounts are optional: a guest creates, joins and plays rooms as before. An account is a username and a password, with an avatar, a record of the games played, titles that matches award, and, if its owner wants, an email address for resetting a forgotten password. Nothing else about the person is collected: no address, no browser, and the email address itself is never kept.

- **Usernames** follow the rules of nicknames, with at least 2 characters, may not mix Latin, Greek and Cyrillic letters, which could pass for one another, and may not be reserved names such as "admin" or "Reviewer 2". Two names are the same when they agree after NFKC normalization, without the silent characters, and with case folded (`usernameKey()` in `shared/src/accounts.ts`); no two accounts have the same, and a guest's nickname may not be one. A username can be changed, with no wait, and the old one is free at once.
- **Passwords** have 8 to 128 characters after NFKC normalization, and nothing else is asked of them. They are kept as scrypt hashes, with N = 2^15, r = 8 and p = 3, which take 32 MiB and about 115 ms on the server, a random salt of 16 bytes, and the parameters beside the hash, so that a hash made with older ones still verifies and is made again at the next login (`server/src/accounts/passwords.ts`). At most two hashes are worked on at a time, and 32 more wait; past that the server answers `busy`.
- **Logins.** A login is a secret of 32 random bytes in a cookie, and the database keeps its SHA-256 (`sessions`). The cookie is `HttpOnly`, `SameSite=Lax`, `Path=/` and, unless `COOKIE_SECURE=0`, `Secure` and named with the `__Host-` prefix, which no other host under the domain can set. It lasts a year in the browser; on the server, a login ends after 30 days without use, after a year in any case, and when its owner logs out, changes or resets the password, or deletes the account. An account may be logged in on 20 browsers, and a 21st ends the one used longest ago. Logging in always makes a new secret, and ends the one the browser had. Every hour, with the contacts, the server deletes the logins and the links in mails that have ended.
- **Connections.** The handshake reads the cookie, from the site's own pages only (below), and a connection that is logged in takes its member key from the account ([Players and identity](#players-and-identity)). When a login ends, the server tells its connections with `account:ended` and closes them; they come back through a new handshake as whoever their browser is then, so that a stolen login, once ended, no longer has the seat. A password change ends the login that it was made with too, since the server can't tell that browser's connections from those of someone who has the same secret; that browser comes back with its new login. A seat that a browser took as a guest becomes its account's when the browser has logged in or registered since and comes back to the room, by the handshake or by asking to join: the player keeps the seat, the team and the role, and is called by the username unless someone in the room has it.
- **Rooms.** A player with an account is called by the username in every room, and a rename of the account, or a new avatar, reaches the rooms it is in at once, unless someone in a room has the new name. A deleted account leaves every room it was in, as if it had left. Pages of a room have no way to log in or out.
- **Records.** When a game ends, the room asks the game how each player did (`GameModule.results()`), and keeps that on the record of every player with an account who took part: the team word guessing game gives the group, the role, the winner and the decision letter of everyone in a seat, and nothing for a game that the chair withdrew. A game is recorded once for each account. The account's page shows how many games it has played and won, and the last 20.
- **Titles** (`TitleStore.award()` in `server/src/store/records.ts`), "Best Paper Award" and "Game black hole", are awarded by matches ([Matches](#matches)); the account's page shows how often it has each, and lists the matches that the account finished, with its place, total and title.

### The account API

`ACCOUNT_API` in `shared/src/accounts.ts` names the addresses. Every answer is JSON, `{ ok: true, ... }` or `{ ok: false, error }` as the messages are answered, with a status code that says the same. The account API is HTTP rather than Socket.IO because only an HTTP response can set the login cookie, which the page's scripts never see.

| Address | Needs | What it does |
|---|---|---|
| `GET /api/account` | | The account that the browser is logged in to, or null, and whether accounts have email on this server |
| `GET /api/account/records` | A login | The record of games |
| `POST /api/register` | | `username`, `password`: creates an account and logs the browser in to it |
| `POST /api/login`, `POST /api/logout` | | Logs the browser in or out |
| `POST /api/account/username` | A login | Renames the account |
| `POST /api/account/avatar`, `POST /api/account/avatar/remove` | A login | Uploads an avatar, as the image itself, or goes back to the default one |
| `POST /api/account/password` | A login, the password | Changes the password: every login ends, and this browser gets a new one |
| `POST /api/account/email`, `POST /api/account/email/remove` | A login, the password | Asks for a link that binds an address, or unbinds the one bound |
| `POST /api/email/confirm` | The link | Binds the address that the link was for |
| `POST /api/password/forgot` | | Asks for a link that resets the password |
| `POST /api/password/reset` | The link | Sets a new password: every browser is logged out, and this one in |
| `POST /api/account/delete` | A login, the password | Deletes the account and everything of it |

Every request that changes something must come from a page of this site: its `Origin`, which browsers send with every POST, names the request's own host, or, without one, its `Sec-Fetch-Site` is `same-origin`. Its body is JSON of at most 4 KB, or an image for the avatar, neither of which a page elsewhere can send without asking first, and the server never allows it. The handshake of a connection that comes from elsewhere doesn't read the login cookie at all.

Only the answers that log the browser in or out set the login cookie. A cookie whose login has ended elsewhere is left as it is, and the request is a guest's: the page asks who it is right after a login or a password change, and the answer to that, with the cookie as it was, may arrive after the answer that set the new cookie, and must not take it away again.

### Limits

All of these are counted in memory, on the clock that only runs forward, and start again when the server does (`server/src/accounts/limits.ts`). Each counts before the password's hash is awaited, so that requests which arrive together can't all pass a limit before any is counted; what comes to nothing, such as a password that proves right, is given back.

- each address may create 5 accounts an hour, or as many as `ACCOUNTS_PER_HOUR` allows ([development.md](development.md)), and be refused 30 times an hour, as for names that are taken;
- wrong passwords, at a login or where an action asks for the password: 20 a minute from an address, and 10 in 15 minutes and 50 a day for a name. A name is counted by its key whether or not an account has it, so that being refused, `login_limited`, says nothing about it. Where an action of an account that is logged in asks for the password, the wrong ones count against the account rather than the name, so that whoever types wrong passwords at the login page doesn't keep the owner from changing theirs. A password that is reset clears the name's count and the account's, and a login that is refused leaves the browsers that are logged in as they are;
- each address may hear 30 times an hour that a guest's nickname is someone's username, `name_reserved`, which says that the account exists, as registering the name would (`server/src/core/socket.ts`); past that, every nickname from the address is refused, `rate_limited`, for the rest of the hour, since being let in would say as much. The reserved names, which a guest may not take either, are public and don't count;
- each address may make 60 requests that change something a minute;
- each account may ask for 3 links to confirm an address a day, each address for 10 mails of either kind an hour, and each address that mails go to for 3 links to reset a password an hour, whether or not an account has it;
- each account may change its avatar 10 times a day.

## Mail

Email is only for resetting a forgotten password. An account binds an address with a link that the address is mailed, and the database keeps its fingerprint: the HMAC-SHA256 of the address, normalized (trimmed, NFKC, in lower case, with the domain in punycode), with a key that HKDF derives from the server's secret, `SERVER_SECRET` ([development.md](development.md)). The secret is not in the database, so whoever reads the database can't tell which addresses are there, not even by trying a list of them. An address is bound to one account at most. Without both the secret and the mailer, accounts have no email: the pages don't offer it, and the API answers `mail_unavailable`. A server that starts with another secret than before can't match the fingerprints that were made with the old one, so it unbinds every address, uses up the links that were to bind one, and logs `addresses_unbound`; the database keeps the fingerprint of a fixed text, by which the change is told.

- **Binding** asks for the password, since an address can reset it: whoever has a login and not the password must not be able to bind an address of their own. The link works once, for 24 hours, and does nothing until its page's button is pressed, so that a mail filter that opens the links in a mail binds nothing. Whether or not another account has the address, the answer is the same and the account has an address waiting to be confirmed; only the mail isn't sent then. An address that the account has already is mailed to as any other, since that tells its owner nothing new. A link to an address that another account bound in the meantime is refused like an expired one.
- **A forgotten password.** The answer to an address is the same whether or not an account has it, and comes before anything is looked up; then, if an account has it, a link that works once, for 30 minutes, is mailed. Setting a new password with it uses up every other link in a mail of the account, logs the account out everywhere, and logs the browser in. A password that is changed, and an address that is unbound, use up the links too, so that one asked for while someone else had the password is of no use to them once the owner has acted; and binding another address uses up the links to reset the password, which went to the address before.
- **The links** lead to `/account/confirm` and `/account/reset` with the secret after a `#`, so that it never reaches a server, a proxy or a log as part of an address, nor a `Referer`. The page takes it and leaves it out of the address bar at once. The database keeps the SHA-256 of each link's secret (`email_tokens`).

### The mailer

`mailer/` is a program of its own, and the only one that holds the key of the mail service. It writes two mails, from its own templates, in Chinese and in English (`mailer/src/locales/`): one that confirms an address, and one that resets a password. Nothing in them comes from a player, not even the username.

- **The way to it** is a Unix socket on the same machine, which the game server's lack of a network doesn't stop. A request is one line of JSON with exactly five fields, `{"v": 1, "kind", "to", "token", "language"}` (`shared/src/mail.ts`), and the answer one line, `{"ok": true}` or an error. The mailer takes nothing else: an address that a mail header could read as more than one, a secret that isn't 43 characters of base64url, or one field more, is `bad_request`. It builds the link itself, from its own idea of the site's address, `MAILER_BASE_URL`, so the game server can't make it write anything else.
- **How many.** At most 50 mails in any 24 hours, of which 40 may confirm an address, so that at least 10 are left to reset passwords whatever anyone does with new accounts. The count is kept in a file in its state directory, and lasts through a restart; every mail handed to the mail service counts.
- **Sending.** It calls Resend's API with `fetch`, from `noreply@playreviewer2.com`, with an idempotency key for each secret, and has no dependencies. `MAILER_TRANSPORT=print` writes each mail out as a line of JSON instead, for development and the end-to-end tests.
- **Its log** says what kind of mail went out, in which language, and how it went, and never to whom or with which secret. The game server logs `mail_requested` with the kind, and `mail_not_sent` when the mailer refused or failed.

In production, systemd starts the mailer from its socket and hands that over; the units are described in [development.md](development.md#running-in-production).

## Avatars

An avatar is always shown as a circle. The page crops the picture that a player chooses to a square, in a round frame, by dragging it and zooming with the slider or two fingers, and encodes it at 256 by 256 pixels as WebP, or as JPEG where the browser can't write WebP, as Safari can't, at lower and lower quality until it fits in 30 KB, down to 0.5. Encoding afresh leaves out everything else that the photo held, such as where it was taken. A player who uploaded none, and every guest, gets a default avatar, which the page draws: the first character of the name on one of eight colors, the same for the same name in any case or width.

- **The server never decodes an image.** It reads only the header: the file must be a WebP or a JPEG by its magic bytes, of 256 by 256 pixels as its header says, a still picture rather than an animation, and of at most 64 KB. So no image decoder runs on the server, and no upload can make the phones of the other players in a room decode a picture far larger than its bytes (`server/src/accounts/avatars.ts`).
- **Files.** An avatar is a file in `avatars/` in `DATA_DIR`, named after the SHA-256 of what it holds, with `.webp` or `.jpg`, and the database keeps the name. Two accounts that upload the same picture share a file, which goes once no account shows it. On start, the server deletes the files that no account shows, and logs `avatars_cleared`. Without `DATA_DIR`, avatars are in memory, as the database is.
- **Served** under `/avatars/<name>`, with the type that its name says, `X-Content-Type-Options: nosniff`, a Content Security Policy that runs nothing, `default-src 'none'`, and `Cache-Control: public, max-age=31536000, immutable`, since a new picture has a new name. Even a file that is a JPEG to its header and HTML after it is shown as an image or not at all.
- **Who sees it.** The name is unguessable without the picture, and only the owner and the players in the same rooms are given it.
- **Taking one down.** The operator runs `server/dist/admin.cjs avatar remove <username> [--ban]`, which takes the avatar down, back to the default, and with `--ban` bars the account from uploading another; `avatar allow <username>` lifts that ([development.md](development.md#running-in-production)). The command works on the database alone, beside the running server, which reads the accounts of the players in its rooms again at every sweep: within a minute, the rooms show the default avatar. Browsers and Cloudflare may keep a copy for as long as it was cached, so the address is also purged from Cloudflare's cache. There is no way for players to report one.

## Threat model

What accounts add, and what keeps each risk small:

- **Guessing passwords, and passwords from other sites.** Slow, salted scrypt; limits on wrong passwords by address and by name, before any hashing ([Limits](#limits)); the same answer and the same work for a name that no account has. The forms let password managers make strong passwords. A password that someone uses elsewhere too can only be as safe as the other site keeps it.
- **Finding out who has an account, or an address.** Usernames are public in rooms, and registering has to say when one is taken, as does joining a room with a guest's nickname that is someone's username, so both are limited per address. Logging in says `login_failed` for a wrong name and a wrong password alike, in the same time. A forgotten password and binding an address get the same answer whatever the address, and the account's page never shows an address, which the server doesn't have.
- **Stealing a login.** The secret is random, kept as its hash, and only in an `HttpOnly`, `Secure`, `SameSite=Lax`, `__Host-` cookie: never in an address, in storage that scripts read, or in the log. It changes at every login and password change, and ends with the logins it belongs to. In production the site is served over HTTPS only, which Cloudflare enforces ([development.md](development.md#running-in-production)).
- **Requests from other sites.** `SameSite=Lax`, the check of `Origin` and `Sec-Fetch-Site` on every request that changes something, bodies that need a preflight, no CORS, and a handshake from elsewhere that ignores the cookie. Pages can't be framed.
- **Scripts that steal.** The login cookie is out of their reach; the Content Security Policy runs only the site's own script, usernames are only ever text, and the rules of names keep hidden and direction characters out. Changing the password, binding an address and deleting the account all ask for the password, so a script in the page can't take an account over. A guest's token is in local storage, as it always was.
- **Links that are replayed or leak.** 256 random bits after a `#`, out of the address bar at once, kept as hashes, for 30 minutes or 24 hours, used up in the transaction that uses them, and the reset link ends every login. Whoever reads the mailbox can reset the password: that is what email recovery is.
- **Mail that is abused.** Two fixed mails with nothing of a player's in them, a mailer that checks every field and builds the links itself, a key that only it holds, a socket that in production only the game server may use, limits per account, address and destination, and 50 mails a day at most whatever happens to the game server.
- **A database that leaks.** It holds usernames, salted scrypt hashes, SHA-256 hashes of random secrets, HMACs of addresses with a key that isn't in it, records and titles, and no addresses, IP addresses or user agents. Should the server's secret leak with it, the addresses could be tried from a list, and the secret is then replaced, which unbinds every address.
- **Uploads.** No image is decoded on the server; only WebP and JPEG of the right size, as their headers say, and of at most 64 KB, are taken; they are served under their own type, with `nosniff` and a policy that runs nothing; and they take at most 2 GB together, with 10 changes a day for an account.

## Logging

The server writes one JSON object per line to stdout: room creation, game starts and ends, a game in which the draw found no way to keep apart words that clash (`words_clashed`, under [Games](#games)), rooms closing, skipped word lists and terms, errors, a warning when it ignores the address that a reverse proxy passed on, and every 5 minutes the `stats` line described under [Status](#status). It never logs tokens.

It also logs how it starts and stops: `database_opened`, with the file or that the database is in memory, `database_migrated`, `listening`, `startup_failed` and `listen_failed` when it can't start, `stopping`, and `stop_timed_out` when stopping took too long. For accounts, it logs `account_created`, `account_deleted` and `password_reset` with the account's ID and nothing else, `mail_requested` and `mail_not_sent` with the kind of mail, `storage_full`, `avatars_full` and `avatars_cleared`, and on start `accounts_per_hour_raised` and `cookies_not_secure` when the settings ask for them, and `addresses_unbound` when the server's secret has changed. For the data, it logs `snapshot_saved` or `snapshot_failed` every hour, `snapshots_not_pruned`, `contacts_cleared` with whether the WAL was truncated and `wal_truncated` for each later try at that, `feedback_received` with the number and kind of each piece of feedback, `feedback_full`, and `feedback_limit_raised` when it starts with a limit above the default. Node's own warnings, such as the one that Node 22 gives on every start because `node:sqlite` is experimental, come as `warning` lines, so that every line of the log is JSON.

A match that runs its course is logged as `match_ended`, with how many games it had.

Every room that was created is logged once more when it closes, with the reason: `empty` when its last member has gone, `idle` or `stale` when the sweep closed it, `chair` when the chair closed it, `restart` when the server stopped. Every game that started is logged once more when it ends, whether it ended by itself or the chair withdrew it; a game is logged as started only, when its room closes in the middle of it. So the log can be counted.

## Status

The operator sees how the server is doing in two ways. `server/src/stats.ts` counts the numbers for both, so they always agree. Neither says who anyone is: there are no addresses, tokens, names or room codes in them, and countries appear only as counts. The page also says how many accounts there are, and nothing else about them. The only exception is the contact that a player may leave with their feedback, which the page shows so that the author can reply.

- **The `stats` log line.** Every 5 minutes the server logs the rooms in each phase, the members online and offline, the connections over WebSocket and over long-polling, the connections from each country, and its memory in megabytes. A line with the same counts as the last one is skipped, so a quiet server writes little; a change in memory alone doesn't count. A line is written once an hour anyway, so that the log shows how the memory goes while nothing else changes. These lines are the only history of the numbers that survives a restart.
- **The status page.** With `STATUS_PORT` set ([development.md](development.md)), the server also listens on that port, on `127.0.0.1` whatever `HOST` says. Only the server's own machine can reach it, which is why it has no password: a reverse proxy or a tunnel leads to the game's port alone. It answers only requests whose `Host` is `localhost` or `127.0.0.1`, so that a web page elsewhere can't point a name of its own at `127.0.0.1` and read the page through a browser on that machine. `/` is the page, `/status.json` has the same numbers for scripts, and `/feedback` is the feedback that players sent. The page is built on the server, has no script and reloads itself every 5 seconds. As a tool for the operator, it is in English only. Besides the numbers of the log line, it shows the version, the uptime, the memory of the process against the limit that the system sets the service, the median latency of each country, and a chart of the players online and the rooms over the last 24 hours, sampled every 30 seconds and kept in memory while the page is on. The page is the operator's alone, so nothing that goes wrong with it may stop the game: an error while it is built is logged and answered with 500, and when its port can't be opened, the server logs `status_unavailable` and runs without the page.
- **Countries** come from the `CF-IPCountry` header that Cloudflare adds to every request it passes on. It is read only with `TRUST_PROXY` on. That setting says only that a proxy adds the player's address to `X-Forwarded-For`; a proxy other than Cloudflare passes a `CF-IPCountry` that a client made up straight through, so [development.md](development.md) asks such a proxy to drop the header. Without the header, every connection counts as unknown.
- **Feedback.** The status page says how much feedback players have sent ([Feedback](#feedback)) and links to `/feedback`, a page of its own on the same port, which shows it newest first, 50 at a time, with a link to the older ones, `/feedback?before=<number>`, and back to the latest. Each shows its number, kind, time, version, language and page, its text, its contact, and the user agent of a bug. That page doesn't reload itself, so that a long bug report can be read and a contact copied in peace. Strangers wrote the feedback, so all of it is escaped like everything else on the pages, and their Content Security Policy runs no script even if something got through. Both pages stay read-only: they read the database and write nothing. `/status.json` has no feedback.
- **Latency** is the round trip of Engine.IO's heartbeat: the server pings every connection every 10 seconds, and the client answers at once. The clock starts when the ping goes out, not when it is queued, which on long polling can be a poll later. The page shows the median of the last heartbeats of each country's connections. The latency stays out of the log, because it never stays the same.
